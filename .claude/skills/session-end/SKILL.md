**向きは「誰が書くか」で決まる**（2026-08-01 に運用規約が訂正された）。

## 実行順序（この順を厳守）

```
① 今セッションの棚卸し
② docs/DECISION_LOG.md 更新（設計判断があった場合のみ）
③ docs/SESSION_STATE.md 更新（毎回）
③-b docs/CURRENT_SPEC.md 更新（仕様が変わった場合のみ）
④ git commit
⑤ Notion へ反映（a: DECISION_LOG＝正本へ追記 / b: SESSION_STATE の写しページを上書き / c: CURRENT_SPEC の生成物ページを全置換）
⑥ 検証（全部を読み直す）
⑦ タスクの棚卸し（週に1回。前回から7日以上経っていたら実施）
```

④を⑤より先に置く理由：git は戻せるが Notion の書き戻しは戻しにくい。途中で失敗しても手元に成果が残る状態を作る。

★ **③-b と ⑤-c は必ずセットで行う。片方だけで終わらせない。**

## ① 今セッションの棚卸し

作業ログを遡り、次を分類する。ユーザーに聞く前に自分で分類すること。

- **設計判断**（仕様・方針を決めた／却下した）→ ②へ
- **仕様が変わった**（現行仕様の記述が古くなった。実装だけでなく規則・基準値・判定の入力が変わった場合を含む）→ ③-b へ
- **実装のみ**（既定の仕様どおりに作った）→ ②③-b はスキップ、③のみ
- **未解決のまま終わる論点** → ③の「未確定項目」へ

判断に迷ったら「この決定を半年後の自分が知らなかったら困るか」で判定する。困るなら設計判断。

★ **設計判断と仕様変更は別物。** DECISION_LOG は「なぜそう決めたか」、CURRENT_SPEC は「今どうなっているか」。片方だけ書いて終わらせない。

## ② DECISION_LOG.md 更新

既存フォーマットに合わせて追記する。**追記位置（冒頭か末尾か）はファイル側の規約に従う。** ファイルに明記がなければ既存エントリの並び順から判断する。日付は実際の日付を確認して使う。

項目：`# YYYY-MM-DD｜<決定を1行で>` の見出しの下に、**決定** ／ **理由** ／ **却下した案** ／ **根拠・参考** の4つ。

★ **「却下した案」を空欄にしないこと。**
却下案と理由を残すのがこのログの主目的。将来のAIが同じ案を再提案するのを防ぐため。却下案が本当に無かった場合のみ「なし（対立案が出なかった）」と明記する。

## ③ SESSION_STATE.md 更新

3項目を必ず埋める。前回の内容を消さず、現在の状態に**上書き更新**する。

- **現在の進捗**：何がどこまで動いているか
- **次にやること**：次のセッションの最初の一手。曖昧な表現にしない
- **未確定項目**：判断待ちで止まっているもの

冒頭に更新日を書く。日付は推測せず確認する。

★ **1行目の正本宣言を消さない。** 上書き更新のときに落とさないこと。

## ③-b CURRENT_SPEC.md 更新（仕様が変わった場合のみ）

★ **2026-08-01 裁定：`docs/CURRENT_SPEC.md` が仕様の正本で、Notion 側は生成物。**

### なぜこの向きか

CURRENT_SPEC は**実装を見て Claude Code が書き、チャット側と作者が読む**文書。判断は DECISION_LOG に、思想はコアコンセプトに残る。**CURRENT_SPEC が持っているのは「今どうなっているか」だけ。** SESSION_STATE と同じ分類に入る。

### なぜ「文言を一致させる」ではないか

3. バッククォート内の日本語とコードブロックが Notion で壊れる

★ **「一致させる」は実質「片方を生成物にする」という意味にしかならない。** それなら明示的にそうする。

### 手順

1. 今回の変更が CURRENT_SPEC のどの節に影響するかを**列挙する**。影響がなければここは飛ばし、⑥で「今回は仕様に影響なし」と明示的に報告する（黙って飛ばさない）
2. `docs/CURRENT_SPEC.md` を直す。**ここが唯一の書き場所**
3. ⑤-c へ進む。★ **片側しか当たらなければ停止する**（「あとで直す」にしない。それが 2026-08-01 にずれた原因）

## ⑤-c CURRENT_SPEC を Notion へ（③-b をやった場合のみ・2026-08-01 追加）

★ **ここもページ全体を置き換える**。Notion 側は**生成物**なので、部分更新にすると古い行が残る。

手順：

- ※ `.md` で終わるファイル名は Notion 側で自動リンク化される。**見た目のノイズだけなので直さなくてよい**（直そうとして本文をいじる方が危険）

## ⑦ タスクの棚卸し（週に1回・2026-08-04 追加）

**毎回ではない。前回から7日以上経っていたら実施する。** 前回いつやったかは `docs/SESSION_STATE.md` の進捗に残る（初回は 2026-08-04 の EX-051）。

`_tasks/進行中` の各件について、次を出す。

- **判定**：完了 ／ 廃止 ／ 重複 ／ 未着手（意図的） ／ 未着手（放置）
- **逆方向も見る**：完了済みに入っているが、**「完了時にやること」が残っていないか**（CURRENT_SPEC の更新・DECISION_LOG への記録など）
- **重複を見つける**：同じことを扱っているページが2枚ないか
- **前提が崩れたものを見つける**：タスクを切ったときの前提が、その後の裁定で崩れていないか
- **根拠は必ず出す**：どの commit ／ DECISION_LOG のどのエントリ ／ どの完了報告か。**推測で判定しない**

★ **タスクを作る前に、進行中の一覧を見る。** 既存を確認せずに新規作成して重複が起きた実例が2回ある（2026-07-27 の EX-022、2026-07-31 の EX-041）。

★ **廃止の明記は、廃止するページ自身に書く。** 吸収先のページにだけ書いても、廃止側を見た人には伝わらない（EX-037 が「未着手（優先）」のまま3週間残っていた）。

※ **ページの移動と廃止は裁定後に行う。** 棚卸し自体は調べて判定するだけ。

# 停止条件

以下に当たったら、作業を止めてユーザーに判断を仰ぐ。勝手に決めて記録すると、誤った内容が正本に入る。

1. 今回の決定が Notion の既存記述と矛盾する
2. 今回の決定が DECISION_LOG で既に却下済みの案に該当する
3. 設計判断かどうかの分類がつかない
4. Notion のどのページに書くべきか判断がつかない
5. コミット対象に意図しないファイルが含まれている
6. **検証の修正を 2 回試しても通らない**（2026-08-04 追加）
7. **CURRENT_SPEC のローカルと Notion の片側しか当たらない**（③-b と ⑤-c はセット。片方だけ成功した状態で進めない）

## 停止時に出力する形式（2026-07-29 改訂：4項目→7項目）

「止まりました」だけでは判断できない。必ず次の**7項目**を出す。

★ 順序と項目数は `02_operations/ドキュメント運用規約`「貼り付けブロック」節に合わせること。欄の名前や区切りの整形は変えてよいが、**数と順序は変えない**。

1. **見出し**：要裁定とタスク名
2. **ページIDと、書いた節の名前**
3. **論点**（1行）
4. **A の内容**（1行。推奨があればその旨）
5. **B の内容**（1行）
6. **トレードオフ**（A と B をそれぞれ一言）
7. **既に却下済みの案があればそれ。なければ「なし」**

★★ **規則（ここが要）**

- このブロックは**要約であって正本ではない**。正本はタスクページ
- **ブロックだけ読んで裁定できる粒度にする。「詳細はページ参照」で済ませない。** それをやるとチャット側がページを全文取得することになり、トークン消費が大きい。**節約のための仕組みなので、粒度を落とすと目的が消える**
- 最後は **A/B の一問一答で答えられる形**まで畳む（ユーザーは移動中に音声で返答することがある）

## 停止時の書き込み先（2026-07-27 追加）

停止ブロックは**画面に出すだけで終わらせない。** その企画の **SESSION_STATE の「判断待ち」節**にも同じ内容を書く。

★★ **書き先は企画ごとの向きに従う**（上の節を参照）：

- **repo が正本の企画**（遠征）：まずローカルの `docs/SESSION_STATE.md` に書き、そのあと ⑤-b で写しを上書きする（写しに直接書くと次の上書きで消える）
- **Notion が正本の企画**（天使様）：**Notion のページに直接書く**。ただし**全置換しない**。`update_content` で「判断待ち」節だけを外科的に追加する
- 書き込む内容は**上の7項目そのまま**
- **日時**と、**どのタスクページの作業か**（ページ名とID）を添える
- 「判断待ち」節が無ければ新設する
- ★ **判断が済んだら、次のセッションでその節を消す。** 残すと「複数の文書が現行を名乗る」状態になる
- ★ **この取り決めは session-end に限らない。** もともとの目的が「セッション**途中**の停止が受け渡しの対象外だった穴を塞ぐ」ことなので、**作業中に判断を仰いで停止するとき全般に適用する**

### ページID の引き方（⑤と同じ規則）

SESSION_STATE ページの ID は `CLAUDE.md` の「Notion ページID」節を参照する。
記載がなければ、またはその企画に SESSION_STATE ページがまだ無ければ、**そこで停止してユーザーに尋ねる**（検索で当てにいかない）。

★ **「SESSION_STATE」は同名ページが複数実在する。** 天使様（IGPJ_02）配下の `SESSION_STATE（現在地）` と、遠征ギルドログ配下の `SESSION_STATE（写し・閲覧用）`。**検索すると別企画のページを踏む**ので、必ず `CLAUDE.md` のページID 節から引くこと。

### なぜこうするか

- チャット側（設計担当の Claude）は Notion を読める。**読む先が1箇所に決まっていれば、ユーザーは「判断待ち見て」と言うだけで済む**
- 現状は停止ブロックが Claude Code の画面にしかないため、ユーザーが手でコピーしてチャットに貼っている。これが受け渡しに残った最後の手作業
- 限界：チャット側の Claude は自分から起動できない。**消えるのは「長文をコピーして貼る」であって「見に行く」ではない**

# 完了時に出力する形式（2026-07-29 新規）

セッションを終えるときも、タスクページに詳細を書いたうえで、**チャットにそのまま貼れる短いブロック**を最後に出す。

**5項目**（順序と数は変えない）：

1. **見出し**：完了とタスク名
2. **ページIDと、書いた節の名前**
3. **やったこと**（3行以内）
4. ★**指示からはみ出した点・未対応**
5. **commit**

★★ **項目4を空にしない。なければ「なし」と書く。** 欄があれば、自発的な申告に頼らず構造的に出てくる。

このブロックを出したあと、**次のセッションで最初にやることを1行**で示して終わる。

# やらないこと

- ユーザーに確認せずに新しい仕様を決める
- 却下済みの案を「改善案」として再提案する
- Notion のページを丸ごと書き換える（**例外は ⑤-b の SESSION_STATE 写しページと、⑤-c の CURRENT_SPEC 生成物ページだけ**）
- 記録を省略して「完了しました」とだけ返す
