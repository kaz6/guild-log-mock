## 冒頭に置く前提

このリポジトリでは **Notion が正本、`docs/` は写し**。
ローカルの `docs/` への追記は暫定記録であり、**Notion へ反映して初めて正本になる**。このスキルはその反映を漏れなく行うためのもの。

### ★ ただし SESSION_STATE だけは向きが逆（2026-07-27 追加）

**SESSION_STATE は repo が正本、Notion が写し。**

- 理由：仕様と設計判断は**人が決めて Notion に書く**が、SESSION_STATE は **Claude Code が生成して Claude Code が読む**。Notion を正本にすると、生成したものを人が手で運ぶ工程が発生し、運び忘れた瞬間に**古い現在地を配る文書**になる。
- Notion 側の写しは**スマホから現在地を見るための閲覧用**。このスキルが毎回上書きするので、人が手で編集してはいけない。
- どの文書がどちら側かは、**各文書の冒頭の宣言を見て判断する**（運用規約の「すべての文書は冒頭で自分がどちら側かを名のる」節）。

## 実行順序（この順を厳守）

```
① 今セッションの棚卸し
② docs/DECISION_LOG.md 更新（設計判断があった場合のみ）
③ docs/SESSION_STATE.md 更新（毎回）
④ git commit
⑤ Notion へ反映（a: DECISION_LOG＝正本へ追記 / b: SESSION_STATE の写しページを上書き）
⑥ 検証（両方を読み直す）
```

④を⑤より先に置く理由：git は戻せるが Notion の書き戻しは戻しにくい。途中で失敗しても手元に成果が残る状態を作る。

## ① 今セッションの棚卸し

作業ログを遡り、次を分類する。ユーザーに聞く前に自分で分類すること。

- **設計判断**（仕様・方針を決めた／却下した）→ ②へ
- **実装のみ**（既定の仕様どおりに作った）→ ②はスキップ、③のみ
- **未解決のまま終わる論点** → ③の「未確定項目」へ

判断に迷ったら「この決定を半年後の自分が知らなかったら困るか」で判定する。困るなら設計判断。

## ② DECISION_LOG.md 更新

既存フォーマットに合わせて追記する。**追記位置（冒頭か末尾か）はファイル側の規約に従う。** ファイルに明記がなければ既存エントリの並び順から判断する。日付は実際の日付を確認して使う。

項目：`# YYYY-MM-DD｜<決定を1行で>` の見出しの下に、**決定** ／ **理由** ／ **却下した案** ／ **根拠・参考** の4つ。

★ **「却下した案」を空欄にしないこと。**
却下案と理由を残すのがこのログの主目的。将来のAIが同じ案を再提案するのを防ぐため。却下案が本当に無かった場合のみ「なし（対立案が出なかった）」と明記する。

## ③ SESSION_STATE.md 更新

3項目を必ず埋める。前回の内容を消さず、現在の状態に**上書き更新**する。

- **現在の進捗**：何がどこまで動いているか
- **次にやること**：次のセッションの最初の一手。曖昧な表現にしない
- **未確定項目**：判断待ちで止まっているもの

冒頭に更新日を書く。日付は推測せず確認する。

★ **1行目の正本宣言を消さない。** SESSION_STATE の冒頭には「このファイルが正本で、Notion 側は写し」という宣言がある。上書き更新のときに落とさないこと。

## ④ git commit

`git add -A` → `git status` で意図しないファイルが混ざっていないか確認 → `git commit`。
コミットメッセージは実際の変更内容と一致させる。「更新」「修正」だけの内容のないメッセージにしない。

## ⑤ Notion へ反映

対象ページの ID は `CLAUDE.md` の「Notion ページID」節を参照する。
記載がなければ**そこで停止し、ユーザーに ID を尋ねる**（検索で当てにいかない）。

★ 同名ページの取り違えが実際に起きている（2026-07-26、遠征の作業中に「DECISION_LOG」で検索して天使様配下のページがヒットした）。

- 追記は `insert_content` を `position: end` で
- 既存記述の書き換えは `update_content` の `old_str` / `new_str` で外科的に
- **ページ全体を置換しない**
- Notion の既存記述と今回の決定が矛盾する場合、**上書きせず停止**する

## ⑤-b SESSION_STATE の写しを Notion へ（毎回・2026-07-27 追加）

★ **ここだけはページ全体を置き換えてよい**（`replace_content`）。上の「ページ全体を置換しない」の唯一の例外。理由：このページは**写し**なので repo と一致させるのが正しい。部分更新にすると古い行が残って写しでなくなる。

手順：

1. 写しページの ID を `CLAUDE.md` の「Notion ページID」節から引く（検索しない）。登録がなければ**停止して尋ねる**
2. 先頭に**スキルが自動で**次の3行を付ける。人が付け忘れる余地を残さない
   - 更新日時（年月日と時刻。**推測せずコマンドで確認する**）
   - これは写しであって正本ではないことと、正は repo の `docs/SESSION_STATE.md` であること
   - このページを手で編集しても repo には戻らないこと
3. 本文はローカルの `SESSION_STATE.md` と同じ内容にする。ただし**書き込みバグを避ける変換をかける**（下記）
4. 書いたら**必ず `notion-fetch` で読み直す**

### 書き込み前にかける変換（壊れるのを防ぐ）

- **バッククォートの中の日本語を外す**（太字に置き換える）。英数字だけのバッククォートはそのままでよい
- **コードブロックを使わない**（日本語を入れると確実に壊れる）
- **サロゲートペアの絵文字を本文に入れない**。ページアイコンは icon パラメータで設定する
- ※ `.md` で終わるファイル名は Notion 側で自動リンク化される。**見た目のノイズだけなので直さなくてよい**（直そうとして本文をいじる方が危険）

# 停止条件

以下に当たったら、作業を止めてユーザーに判断を仰ぐ。勝手に決めて記録すると、誤った内容が正本に入る。

1. 今回の決定が Notion の既存記述と矛盾する
2. 今回の決定が DECISION_LOG で既に却下済みの案に該当する
3. 設計判断かどうかの分類がつかない
4. Notion のどのページに書くべきか判断がつかない
5. コミット対象に意図しないファイルが含まれている

## 停止時に出力する形式

「止まりました」だけでは判断できない。必ず次の4点を出す。

```
【論点】<何を決める必要があるか・1行>

【選択肢】
A: <案>
B: <案>

【トレードオフ】
A: 得られるもの / 失うもの
B: 得られるもの / 失うもの

【却下済みか】
DECISION_LOG を確認した結果：<既出の有無。既出ならその日付と理由>

→ A / B どちらにしますか
```

★ 最後は **A/B の一問一答で答えられる形**まで畳むこと。ユーザーは移動中に音声で返答することがある。

## 停止時の書き込み先（2026-07-27 追加）

停止ブロックは**画面に出すだけで終わらせない。** その企画の **SESSION_STATE（Notion 側の写しページ）の「判断待ち」節**にも同じ内容を書く。

- 書き込む内容は**上の形式そのまま**（論点／選択肢／トレードオフ／却下済みか）
- **日時**と、**どのタスクページの作業か**（ページ名とID）を添える
- 「判断待ち」節が無ければ新設する
- ★ **判断が済んだら、次のセッションでその節を消す。** 残すと「複数の文書が現行を名乗る」状態になる
- ★ **この取り決めは session-end に限らない。** もともとの目的が「セッション**途中**の停止が受け渡しの対象外だった穴を塞ぐ」ことなので、**作業中に判断を仰いで停止するとき全般に適用する**

### ページID の引き方（⑤と同じ規則）

SESSION_STATE ページの ID は `CLAUDE.md` の「Notion ページID」節を参照する。
記載がなければ、またはその企画に SESSION_STATE ページがまだ無ければ、**そこで停止してユーザーに尋ねる**（検索で当てにいかない）。

★ **「SESSION_STATE」は同名ページが複数実在する。** 天使様（IGPJ_02）配下の `SESSION_STATE（現在地）` と、遠征ギルドログ配下の `SESSION_STATE（写し・閲覧用）`（2026-07-27 新設）。**検索すると別企画のページを踏む**ので、必ず `CLAUDE.md` のページID 節から引くこと。

★ 遠征の写しページは**閲覧用の写し**であって正本ではない。「判断待ち」節を書くときは、**まずローカルの `docs/SESSION_STATE.md` に書き、そのあと⑤-b で写しを上書きする**（写しに直接書くと次の上書きで消える）。

### なぜこうするか

- チャット側（設計担当の Claude）は Notion を読める。**読む先が1箇所に決まっていれば、ユーザーは「判断待ち見て」と言うだけで済む**
- 現状は停止ブロックが Claude Code の画面にしかないため、ユーザーが手でコピーしてチャットに貼っている。これが受け渡しに残った最後の手作業
- 限界：チャット側の Claude は自分から起動できない。**消えるのは「長文をコピーして貼る」であって「見に行く」ではない**

出典：`02_operations/ドキュメント運用規約`「Code → チャット の受け渡し」

# やらないこと

- ユーザーに確認せずに新しい仕様を決める
- 却下済みの案を「改善案」として再提案する
- Notion のページを丸ごと書き換える（**例外は⑤-b の SESSION_STATE 写しページだけ**。写しなので全置換が正しい）
- 記録を省略して「完了しました」とだけ返す
