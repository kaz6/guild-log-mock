## ★ 写しを作るときに短縮しない（2026-09-15 追加・EX-100）

★ **列挙は列挙のまま写す。** 箇条書きを1行に畳んだり、観点の並びを要約したりしない。

- ⚠️ **根拠**：2026-09-14 にマスターと突き合わせたところ、**セルフレビューの「渡す観点5つ」が写しでは1行に潰れていた**。

- ★ **「読めば同じ」に見えても、観点が列挙されていないと実行時に落ちる。**
  読むときは足りているように見え、**使うときに初めて欠けていることが分かる**——
  しかも欠けた側は何も言わないので、**気づく機会がない**。
- したがって写しでよいのは**整形だけ**（見出しの階層・欄の名前・区切り）。
  ★ **中身の粒度を落とすのは整形ではない。**
- ⚠️ 逆に、写し側が独自に**足した**説明はそのまま残してよい（マスターの内容を削っていない限り）。

## 冒頭に置く前提

**向きは「誰が書くか」で決まる**（2026-08-01 に運用規約が訂正された）。

| 誰が書くか | 正本 | 例 |
|---|---|---|
| **人・チャットが決めて書く** | **Notion** | DECISION_LOG／コアコンセプト／タスクページ／運用文書 |
| **Claude Code が生成する** | **repo** | SESSION_STATE／CURRENT_SPEC |
| **実装から導出できる事実** | **コード** | 依頼一覧／解放ツリー／各種の表 |

★ 「Notion が正本」は**原則の言い方として不正確**。そう読んだせいで、2026-08-01 に CURRENT_SPEC の正本（Notion）が写し（ローカル）より古くなる事故が起きた。

★ **ローカルへの追記が暫定記録になるのは、Notion が正本の文書だけ。** repo が正本のものは、**ローカルが正で Notion が生成物**。「ローカルは常に暫定」と読むと向きを取り違える。

このスキルは、正本と写し・生成物の反映を**両方向とも**漏れなく行うためのもの。

## ⓪ origin と同期しているかの確認（毎回・2026-08-09 追加）

★ **何をする前でも、まずこれを見る。** 作業ツリーが古いまま生成物を作ると、
**欠けた入力から作られた出力が「全件」の顔をして出来上がる。**

```bash
git fetch origin <ブランチ名>
git rev-parse --short HEAD
git rev-parse --short origin/<ブランチ名>
git rev-list --left-right --count HEAD...origin/<ブランチ名>   # 左＝ローカル先行 / 右＝origin 先行
```

- **右が0でない＝ローカルが巻き戻っている。** 作業前に早送りする
  （`git merge --ff-only origin/<ブランチ名>`。ローカル側にコミットがあるなら**停止して尋ねる**）
- ★ **一致を目で確かめるだけにしない。数を出す。** 「たぶん最新」で作業した結果が EX-066 の事故
  （コンテナが 2026-07-26 時点のクローンで起動しており、DECISION_LOG が 63件中17件しか無かった。
  **origin には全件あった**）
- ★ **報告に「作業時点の HEAD と、origin との一致」を1行入れる**（測定に日付・時刻・HEADハッシュを
  併記するのと同じ拡張）。**一致していたことも書く**——書かない運用にすると、確認したかどうかが残らない

⚠️ **生成物を作る作業は、このスキルの外でも同じ確認から始める**（`CLAUDE.md` にも同じ規則がある）。
**生成物は網羅性が命で、入力が欠けても出力は正常に見える。**

## ① 今セッションの棚卸し

作業ログを遡り、次を分類する。ユーザーに聞く前に自分で分類すること。

- **設計判断**（仕様・方針を決めた／却下した）→ ②へ
- **仕様が変わった**（現行仕様の記述が古くなった。実装だけでなく規則・基準値・判定の入力が変わった場合を含む）→ ③-b へ
- **実装のみ**（既定の仕様どおりに作った）→ ②③-b はスキップ、③のみ
- **未解決のまま終わる論点** → ③の「未確定項目」へ

判断に迷ったら「この決定を半年後の自分が知らなかったら困るか」で判定する。困るなら設計判断。

★ **設計判断と仕様変更は別物。** DECISION_LOG は「なぜそう決めたか」、CURRENT_SPEC は「今どうなっているか」。片方だけ書いて終わらせない。

## ② DECISION_LOG.md 更新

既存フォーマットに合わせて追記する。**追記位置（冒頭か末尾か）はファイル側の規約に従う。** ファイルに明記がなければ既存エントリの並び順から判断する。日付は実際の日付を確認して使う。

項目：`# YYYY-MM-DD｜<決定を1行で>` の見出しの下に、**決定** ／ **理由** ／ **却下した案** ／ **根拠・参考** の4つ。

★ **「却下した案」を空欄にしないこと。**
却下案と理由を残すのがこのログの主目的。将来のAIが同じ案を再提案するのを防ぐため。却下案が本当に無かった場合のみ「なし（対立案が出なかった）」と明記する。

★ **チャット側（設計担当）が正本へ直接書いた節は、そのままローカル写しへ取り込む**（2026-09-14 追加）。
**却下した案の欄が無い形式でよい。** 判断基準の記録は却下を伴わないので、**欄が空なのは欠落ではなく性質**。
却下案索引の「項が無いエントリ」がそのぶん増えるのは**正しい反映**で、減らそうとしないこと。
※ 取り込むときは、**チャット側が書いた節であることを1行で明記する**（写しを読む人が正本の書き手を追えるように）。

## ④-b PR をマージし、main が HEAD を含むことを確認（毎回・2026-09-11 追加）

★ **push しただけでは終わらない。** リモートセッションのコンテナは**既定ブランチ（`main`）からクローンして起動する**ので、
作業ブランチが先行したままだと**次のセッションが古い木で立ち上がる**。

```bash
git push -u origin <ブランチ名>
# PR が無ければ作る（draft なら draft を外す）。そのうえでマージする
git fetch origin main
git merge-base --is-ancestor HEAD origin/main && echo "main は現HEADを含む"
```

- ★ **マージ済みの PR は、同じブランチへ push しても再び open にならない**（2026-09-11 実測）。
  **④-b は毎回「PR が無ければ作る」から始まる。** 1本の PR を使い回す運用にはできない。
- ★ **⓪ の早送りは「古い木で立ち上がったときの手当て」であって、これの代わりにはならない。**
  ⓪ は症状に対処する手順、④-b は**状態そのものを直す**手順（2026-09-11・EX-073 裁定2）。
- ★ **報告に「main が現HEADを含むこと」を1行入れる**（⓪ の HEAD/origin の一致と同じ扱い。**含んでいたことも書く**）。
- ブランチ運用（`claude/…`）は変えない。**main 直押しにはしない**（Web UI から push 先を選べないため）。
- ⚠️ マージできない事情があれば**停止して尋ねる**（勝手に force したり、ブランチを作り直したりしない）。

根拠：2026-09-11 時点で main が 2026-07-27 の `ec5769e` のまま止まり、ブランチが **152 コミット先行**していた。
**EX-066 の事故（コンテナが 2026-07-26 のクローンで起動し、DECISION_LOG が 63件中17件しか無かった）と同じ構造が現存していた。**

### 既知の変換差分（⑤-b と ⑤-c に共通）

★ **下記は Notion 側の仕様であって壊れているのではない。差分箇所に数えないし、直そうとしない**（直そうとして本文をいじる方が危険）。

- **空行が畳まれる**
- **`****` になる**（太字の入れ子）
- ★ **`~~~~` になる**（2026-09-16・EX-111 で実測。取り消し線の中にコードスパンがあると、Notion が前後で `~~` を開き直す。
  **`****` と同じ機構で、本文の文字は1文字も欠けない**）
- ★ **バックスラッシュのエスケープが入る**（例 `\>=`。同じく実測。文字は欠けない）
- ⚠️ ★ **単独のバックスラッシュは、書き込みのときに食われて消えることがある**（2026-09-17 実測。写しの「`\` は別キーの新規になる」が「「」 は別キーの新規になる」になっていた）。**これは欠けるので、既知の変換差分ではなく直す対象**。読み直しで拾うこと
- ★ **太字が行をまたぐと、Notion 側で太字が落ちる**（2026-09-17・EX-117 で実測。`**A\nB**` のように
  `**` の中に改行が入っていると、書き込み後は太字が消えて地の文になる）。**本文の文字は1文字も欠けない**ので
  差分箇所には数えないが、★ **書く側で避けられる**——`**` が1行に収まるように書けば起きない。
- **インデントがタブになる**
- ★ **番号付きリストは自動採番される**ので、ローカル側で番号を振り直しても写しには文字として現れない
- ★ **バッククォートを含む文字列は `update_content` の `old_str` に当たらない**（2026-08-08 追加）。Notion 側でインラインコードとして別スパンに切れているため、地の文と一続きの文字列として照合できない。
  **差分更新のときは、バッククォートを避けた断片を anchor にする**（例：`` `personality` 廃止 `` ではなく「廃止」を含む前後の地の文で当てる）。★ **当たらなかったときに文言が違うと誤診しない。まずバッククォートを疑う。**

### 当たり確認は読み直しだけ（⑤-b／⑤-c／⑤-d に共通・2026-09-11 追加）

★ **書けたかどうかは `notion-fetch` でページを取り直して確かめる。それ以外の手段を当たり確認に使わない。**

⚠️⚠️ **単発 probe（`update_content` に old_str と new_str を同じ文字列で渡す）は廃止した。**
**存在しない文字列を渡しても成功を返す**（照合せずに no-op で返している）ので、**当たり確認として機能していない**。
2026-09-11 に対照実験で確定：

| 渡し方 | 存在しない文字列 | 存在する文字列 |
|---|---|---|
| old＝new | **成功が返る**（＝確認になっていない） | 成功 |
| old≠new | 「No matches」 | 成功 |

- ★ **old≠new で「No matches」が返る側（負の信号）だけは信用できる。** 使ってよいのは
  **「消えたことの確認」だけ**——削除したはずの文字列を old≠new で当てにいき、「No matches」が返れば消えている。
  **「在ることの確認」には使わない。**
- ⚠️ ★ **`notion-search`（ページ内検索）も当たり確認に使わない**（2026-09-11 追加）。
  **書き込み直後は索引が古く、直前に書き換えた値ではなく前の値を返すことがある**（実際に起きた）。
- ★ **大きいページの `notion-fetch` が重いのは受け入れる**（SESSION_STATE の写しで約6万トークン）。
  **確認しないで済ませるより安い。**

根拠：2026-08-08〜08-19 の差分更新で probe だけを当たり確認にした箇所は、**実際には何も確認していなかった**
（内容そのものは 2026-08-19 に `notion-fetch` で読み直して正しいことを確認済み。**遡っての洗い直しは不要**と裁定済み）。

### 差分更新は、投入したオペ数と差分ハンク数を突き合わせる（⑤-b／⑤-c／⑤-d に共通・2026-09-13 追加）

★ **差分更新を選んだら、`git diff` が出したハンクの数と、`update_content` に投入したオペの数を並べて数える。
合わないまま書き込みに進まない。**

- 手順は2行：
  1. 反映済みの時点から今までの差分を取り、**ハンクを番号付きで列挙する**
     （`git diff <前回反映のコミット> -- docs/<対象>.md` の `@@` の数）
  2. `content_updates` に入れたオペを**同じ番号で対応づける**。1つのオペが複数ハンクをまとめて
     当てるなら、**どのハンクをまとめたかを書く**（数が減る理由を残す）
- ★ **報告にもこの2つの数を書く**（⓪の HEAD/origin の一致と同じ扱い。**合っていたことも書く**）
- ★ **合わないときは、合わない理由を明記する**（例：対象の行が写しに存在しない／
  バッククォート回避のため1ハンクを2オペに分けた）。**数が合わないこと自体は失敗ではない。
  黙って合わないのが失敗。**

⚠️ **なぜ読み直しだけでは足りないか：** `notion-fetch` の読み直しは
**「入っているもの」は確認できるが、「入れるべきだったのに入れ忘れたもの」は見つけにくい**。
ページは長く、欠けた側は**何も痕跡を残さない**。数の照合はその穴だけを塞ぐ。

根拠：2026-09-12 の ⑤-b で、**差分4ハンクに対してオペを3つしか投入せず、進捗の1ハンク（4行）が
丸ごと当たっていなかった**。ツールは3件とも成功を返し、読み直しでも
「入っている側」は全部正しく見えた。**翌日にローカルと写しを機械で突き合わせて初めて見つかった**
（欠けていたのは 1,497字）。★ **「成功が返った」も「読み直して正しかった」も、
入れ忘れには効かない。**

## ⑤-c CURRENT_SPEC を Notion へ（③-b をやった場合のみ・2026-08-01 追加）

★ **原則はページ全体を置き換える**。Notion 側は**生成物**なので、部分更新にすると古い行が残る。

★ **（2026-08-06 改訂）次の3条件をすべて満たす場合に限り、全置換でなく差分の外科的更新でよい。**

1. **直前の全置換が同一の生成元から行われている**
2. **前回反映時点からの差分箇所が特定できている**
3. **書き込み後に読み直して検証し、更新箇所を報告に明記する**

満たさない場合（生成元が変わった・差分が特定できない・前回反映からの経過が大きい等）は**従来どおり全置換する**。
理由：全置換は出力を3分割して当てる必要があり、**表ブロックの分割位置を誤ると壊れる**。規約の目的は反映漏れの防止であり、**読み直し検証を必須にすれば差分更新でも目的を満たす**（詳細は遠征の DECISION_LOG 2026-08-06）。

手順：

1. `node scripts/gen-notion-spec.js` を実行する。**変換と宣言3行の自動付与はこのスクリプトが行う**
2. 全置換のとき：出力をそのまま Notion ページへ入れる。長いので、`replace_content` で先頭の塊を入れてから `insert_content`（`position: end`）で継ぎ足す
   差分更新のとき：**前回の生成出力と今回の出力を突き合わせて差分箇所を出し**、`update_content` で1件ずつ当てる
3. 書いたら**必ず `notion-fetch` で読み直し、生成物と突き合わせる**。★ **差分更新のときも同じ**（**単発 probe は使わない**。下の「当たり確認は読み直しだけ」を参照）

### 生成物の宣言（スクリプトが自動で出す。手で書かない）

1. 生成日時
2. これは生成物であって正本ではない。正は repo の docs 配下の CURRENT_SPEC
3. ここを編集しても次の更新で消える

※ 依頼一覧の生成物に付けるのと同じ扱い。**人が付け忘れる余地を残さない。**

- ※ `.md` で終わるファイル名は Notion 側で自動リンク化される。**見た目のノイズだけなので直さなくてよい**（直そうとして本文をいじる方が危険）

※ **書いたあとに現れる差分は、⑤-b の「既知の変換差分」節を先に見ること**（空行の畳み・`****`・タブ・自動採番・バッククォート）。

# 停止条件

以下に当たったら、作業を止めてユーザーに判断を仰ぐ。勝手に決めて記録すると、誤った内容が正本に入る。

1. 今回の決定が Notion の既存記述と矛盾する
2. 今回の決定が DECISION_LOG で既に却下済みの案に該当する
3. 設計判断かどうかの分類がつかない
4. Notion のどのページに書くべきか判断がつかない
5. コミット対象に意図しないファイルが含まれている
6. **検証の修正を 2 回試しても通らない**（2026-08-04 追加）
7. **CURRENT_SPEC のローカルと Notion の片側しか当たらない**（③-b と ⑤-c はセット。片方だけ成功した状態で進めない）
8. **④-b で PR をマージできない**（コンフリクト・権限・保護ルールなど。★ **force したりブランチを作り直したりしない**。2026-09-11 追加）

## 停止時に出力する形式（2026-07-29 改訂：4項目→7項目）

「止まりました」だけでは判断できない。必ず次の**7項目**を出す。

★ 順序と項目数は `02_operations/ドキュメント運用規約`「貼り付けブロック」節に合わせること。欄の名前や区切りの整形は変えてよいが、**数と順序は変えない**。

1. **見出し**：要裁定とタスク名
2. **ページIDと、書いた節の名前**
3. **論点**（1行）
4. **A の内容**（1行。推奨があればその旨）
5. **B の内容**（1行）
6. **トレードオフ**（A と B をそれぞれ一言）
7. **既に却下済みの案があればそれ。なければ「なし」**

★★ **規則（ここが要）**

- このブロックは**要約であって正本ではない**。正本はタスクページ
- **ブロックだけ読んで裁定できる粒度にする。「詳細はページ参照」で済ませない。** それをやるとチャット側がページを全文取得することになり、トークン消費が大きい。**節約のための仕組みなので、粒度を落とすと目的が消える**
- 最後は **A/B の一問一答で答えられる形**まで畳む（ユーザーは移動中に音声で返答することがある）
- ★ **ただし「C：前提が違う／どちらも違う」を常に有効な回答として末尾に明記する**（2026-09-09 追加）。
  **選択肢を2つに畳むと、畳んだ側が枠を決め、答える側はその外が見えなくなる。**
  C が返ってきたら理由を問わず、**論点の立て方からやり直す**。「なんか違う」だけで成立する回答。
  末尾の行は **「→ A / B / C（前提が違う）」** の形にする

### ★ 出す前にセルフレビューをかける（2026-09-12 正式運用。試行導入は 2026-09-11・EX-075【2】）

★ **停止報告は、出す前にサブエージェントへ叩かせる。** 完了報告は対象外（今のところ）。

**渡す観点5つ**（マスターの文言）：

1. ★ この論点は本当に A/B の二択か。二択に畳んだことで、**より良い第三の選択肢が見えなくなっていないか**
2. **前提そのものが間違っていないか**（X すべきかと問う前に、そもそも X が必要かを疑う）
3. 裁定者が**このブロックだけを読んで判断できるか**。欠けている情報は何か
4. **A/B の記述は公平か。** どちらかに誘導していないか
5. **却下済みの案を再提案していないか**

規則：

- ★ **指摘は鵜呑みにしない。効くものは自分で再実測して裏を取る**（レビュー側が誤っていた例も実際にある）
- ★ **レビューで何を指摘され、どう直したか（または直さなかった理由）を、停止報告の末尾に2〜3行で添える**
- ★ **急いでいるときに省かない。** 「今回は明らかだから」で落ちると、運用として残らない

理由：**5回まわして5回とも、出す前に直すべき誤りが出た**（毎回3〜6件）。しかも**論点そのものの取り違え**と、**CURRENT_SPEC に書いた診断そのものの誤り**が含まれていた。★ **停止報告は裁定の入力**なので、ここが間違っていると**間違った前提で下された裁定が正本に残り、後から読んでも気づけない。**

⚠️ 戻す条件：指摘がノイズばかりになった／セルフレビューの指摘をそのまま信じて誤った訂正を入れた。

## 停止時の書き込み先（2026-07-27 追加）

停止ブロックは**画面に出すだけで終わらせない。** その企画の **SESSION_STATE の「判断待ち」節**にも同じ内容を書く。

★★ **書き先は企画ごとの向きに従う**（上の節を参照）：

- **repo が正本の企画**（遠征）：まずローカルの `docs/SESSION_STATE.md` に書き、そのあと ⑤-b で写しを上書きする（写しに直接書くと次の上書きで消える）
- **Notion が正本の企画**（天使様）：**Notion のページに直接書く**。ただし**全置換しない**。`update_content` で「判断待ち」節だけを外科的に追加する
- 書き込む内容は**上の7項目そのまま**
- **日時**と、**どのタスクページの作業か**（ページ名とID）を添える
- 「判断待ち」節が無ければ新設する
- ★ **判断が済んだら、次のセッションでその節を消す。** 残すと「複数の文書が現行を名乗る」状態になる
- ★ **この取り決めは session-end に限らない。** もともとの目的が「セッション**途中**の停止が受け渡しの対象外だった穴を塞ぐ」ことなので、**作業中に判断を仰いで停止するとき全般に適用する**

### ページID の引き方（⑤と同じ規則）

SESSION_STATE ページの ID は `CLAUDE.md` の「Notion ページID」節を参照する。
記載がなければ、またはその企画に SESSION_STATE ページがまだ無ければ、**そこで停止してユーザーに尋ねる**（検索で当てにいかない）。

★ **「SESSION_STATE」は同名ページが複数実在する。** 天使様（IGPJ_02）配下の `SESSION_STATE（現在地）` と、遠征ギルドログ配下の `SESSION_STATE（写し・閲覧用）`。**検索すると別企画のページを踏む**ので、必ず `CLAUDE.md` のページID 節から引くこと。

### なぜこうするか

- チャット側（設計担当の Claude）は Notion を読める。**読む先が1箇所に決まっていれば、ユーザーは「判断待ち見て」と言うだけで済む**
- 現状は停止ブロックが Claude Code の画面にしかないため、ユーザーが手でコピーしてチャットに貼っている。これが受け渡しに残った最後の手作業
- 限界：チャット側の Claude は自分から起動できない。**消えるのは「長文をコピーして貼る」であって「見に行く」ではない**

出典：`02_operations/ドキュメント運用規約`「Code → チャット の受け渡し」および「貼り付けブロック」

# 完了時に出力する形式（2026-07-29 新規）

セッションを終えるときも、タスクページに詳細を書いたうえで、**チャットにそのまま貼れる短いブロック**を最後に出す。

**5項目**（順序と数は変えない）：

1. **見出し**：完了とタスク名
2. **ページIDと、書いた節の名前**
3. **やったこと**（3行以内）
4. ★**指示からはみ出した点・未対応**
5. **commit**

★★ **項目4を空にしない。なければ「なし」と書く。** 欄があれば、自発的な申告に頼らず構造的に出てくる。

このブロックを出したあと、**次のセッションで最初にやることを1行**で示して終わる。
