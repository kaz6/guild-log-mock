# JSバグ修正ループ

## 狙い

このプロジェクトは「機能を小さく足して手触りを見る」段階にあり、バグ修正のたびに触る範囲が広がると導線がすぐ壊れる。修正は「小さく直してすぐ検証する」を1セットとして、最大3周まで回す。3周しても直らないなら、当て推量を続けるより一度止まって原因候補を報告する。

## 手順(1周ごと)

今何周目かを意識しながら進める。

1. **確認** — 何が起きているかを実際に確認する。Consoleのエラーメッセージ、再現手順、症状(押せない/表示されない/崩れている)を具体的に書き出す。あいまいなまま次に進まない。ブラウザで再現できるなら、consoleログを直接確認できるツール(例: mcp__claude-in-chrome の read_console_messages)を使うとよい。
2. **仮説** — 原因を一つの仮説として言語化する。「〜が原因で〜になっている」という形で一文にまとめる。
3. **最小修正** — その仮説を検証するための最小の変更だけ行う。触るファイルは1〜2個まで。ついでの整理やリファクタリングはしない。
4. **検証** — 次の3点を確認する。
   - Consoleに赤いエラーが出ていないか
   - 直したかった操作が実際に動くか
   - 他の画面・機能に影響が出ていないか(AI_GUIDELINES.mdの「壊してはいけない導線」も併せて確認する)

   3点とも満たせたら、この周で完了。変更したファイルと確認手順をユーザーに報告する。

## 直らなかったら

4の検証で直っていなければ、1に戻ってもう1周する。これを最大3周まで。

- 1周目で不成立 → 仮説を見直して2周目へ
- 2周目で不成立 → 仮説を見直して3周目へ
- 3周目でも不成立 → ループを止める(それ以上は推測での修正を重ねない)

## 3周失敗したときの報告

コードを触り続けず、次の形で止めて報告する。

- 試した仮説と結果(最大3つ)
- 残っている原因候補
- 次に試すべき調査・修正の提案

## 触ってはいけない範囲

このループの中では、目の前のバグと直接関係なければ次の範囲には手を出さない。直すために必要に見える場合でも、まず立ち止まってユーザーに確認する。

- セーブデータ構造
- 既存の関数シグネチャ
- HTML全体の構成
- 関係ない他機能のコード
