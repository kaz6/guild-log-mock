# _tasks（実装タスク）

> 遠征ギルドログの**実装タスク**を置く階層。設計ドキュメント（仕様・構想メモ）とは分離する。
> 

# この階層のルール

## 目的

- 「読む用（設計）」と「やる用（タスク）」を混ぜない。
- 設計ページを丸ごと読ませると、却下案や将来構想まで拾ってスコープが広がるため。
- 1タスク＝1ページで、物理的にスコープを区切る（最小差分・1回1機能の原則を守るため）。

## 構造

- **進行中**：これからやるタスク。Claude Code にはここのページを指定して読ませる。
- **完了済み**：終わったタスクの置き場。定期的に削除してよい。

## 使い方

チャットでの指示は1行で済む：

> Notionの「〇〇」タスクページを読んで実装して。作業前に理解確認して。
> 

## 完了・削除のルール（重要）

完了済みフォルダのタスクは定期削除してよいが、**削除しても情報が失われない状態を作ってからにすること**。

タスクを「完了済み」に移す前に、以下を確認：

1. 実装中に行った設計判断が `docs/DECISION_LOG.md` に転記されているか
2. 進捗・次の作業・未確定項目が `docs/SESSION_STATE.md` に反映されているか
3. 確定した仕様がリポジトリの .md または設計ページに反映されているか

→ この3つが満たされていれば、タスクページ自体は消しても安全。

## 役割分担（変更なし）

- **Notion**：進化する草稿、セッション間の共有メモリ、実装タスク
- **リポジトリの docs/*.md**：確定した設計・決定の永続記録（クローンしただけで設計思想を追える状態を保つ）
- Notionだけにしない。DECISION_LOG / SESSION_STATE への記述はこれまでどおり続ける。

# ワークフロー（2026-07-14 確定）

## 流れ

1. **チャットClaude** がタスクページを作成（やること / やらないこと / 制約 / 完了条件）
2. **作者** が Claude Code に「Notionの〇〇タスクを読んで実装して」と指示
3. **Claude Code** が実装 → タスクページの「実装結果」セクションに追記 → docs/*.md を更新
4. **Claude Code** はチャットには短い完了報告のみ返す
5. **作者** がチャットClaude に「読んで」と伝える
6. **チャットClaude** が Notion を読んでレビュー

## 狙い

- チャットは「通知」、Notion が「実体」。同じ内容を二重に書かない。
- Claude Code の出力をチャットに貼り直す手間が消える。
- チャット履歴が流れても、実装結果が Notion に残る。

## タスクページに必ず入れるセクション

- やること（スコープ）
- やらないこと（明示的に除外）
- 制約
- 完了条件（チェックリスト）
- 完了時にやること
- 背景（必要なときだけ読むリンク）
- **実装結果**（Claude Code が記入。変更ファイル / 確認手順 / 決めたこと / 詰まった点 / 完了条件の結果）

# 次にやること候補（2026-07-23 時点）

> スライス7完了時点。次のセッションで「何をやるか」を決めるためのメモ。

## 現在地

- 戦闘の**静的な数値体系**は完成（スライス6：stat 255スケール移行 / スライス7：敵threat調整）。
- 隊商護衛の戦闘ドラマログは、温度・順序・色分け・回復・傷の記録まで一通り動いている。
- **繰延事項**：「勝率80〜90%」「通常編成で撤退が生きる」。根本原因＝**損耗が火力に反映されない（味方DPSが減衰しない）**。

## 候補A：損耗によるDPS低下（繰延事項の本丸）★推奨

- 傷ついた者の与ダメが落ちる仕組みを入れる。
- **これ一つで「本当に負ける」「戦況悪化で撤退が発火する」の両方が解ける。**
- 影響：エンジン構造の変更。導入後は**敵threatの全面再スイープが必要**。
- 注意：悪い戦闘は5Tを超えるが、これは許容（「3〜5Tは典型目標であって上限ではない」＝裁定済み）。
- 補足：撤退は弱編成では既に機能している（ミナ+エルネ19.6%等）。通常編成で撤退が要るのは「格上と当たった時」か「戦況が崩れた時」。前者は敵の格でも解決できるので、**繰延2項目のうち本丸は「勝率」の方**。

## 候補B：納屋・畑の simulateBattle 移行

- 現在この2依頼は simulateBattle を通っておらず、固定シナリオ＋tensionValue で動いている。
- 移行すれば戦闘ドラマログが3依頼で使えるようになる（型の横展開）。
- 影響：中程度。ドラマログの形は確定済みなので、同じ型に流し込むだけ。
- **候補Aの後にやる方が良い**（Aで戦闘の挙動が変わるため、先に移行すると二度手間）。

## 候補C：成長システムの実装

- スライス6で受け皿は用意済み（GROWTH_STAT_MAX 255・育成6種限定の除外リスト）。
- **statが実際に動き始めると、名簿を見る楽しみが生まれる**。
- 影響：中程度。ただし成長でstatが動くと戦闘バランスも動くので、**候補Aの後**が安全。
