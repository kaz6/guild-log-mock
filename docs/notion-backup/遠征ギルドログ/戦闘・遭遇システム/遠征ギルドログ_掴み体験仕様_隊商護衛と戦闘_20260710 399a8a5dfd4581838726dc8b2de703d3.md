# なぜこの設計なのか（売りの確認）

原体験はMPO（メタルギア）のサイバーサバイバル。送り出した部隊が「何をして」「何が起きて」「どう終わったか」の記録を読む面白さが核。プレイヤーは戦場に行かず、帰ってきた記録を読む側。

三層構造：

1. 記録を読む楽しさ（本体）
2. 生き物・不穏な存在を観察・記録・命名し、世界にプレイヤーの痕跡を残す
3. 愛着の湧いた冒険者・受付嬢を守る動機 → アンチミーム的なラスボスの封印

MVP（人に見せる）で見せたいのは第1層。ただし「記録を読む楽しさ」を初見で成立させるには、掴みの依頼で読み応えのあるトラブルと結果を確実に見せる必要がある。牧歌的な薬草採集から始めると売りが伝わらないまま飽きるので、掴みは隊商護衛のようなドラマ型に寄せる。

# 戦闘とドラマの関係（設計の根幹）

戦闘システムと護衛ドラマは別物ではなく、同じ因果の別の顔。

- 護衛ドラマ = 因果の入れ物（物語）
- 戦闘システム = 因果を生むエンジン（数値の挙動）

1本の因果：予兆 → プレイヤーの事前選択 → 交戦の挙動 → 段階的な結果（無傷/負傷/離脱/ロスト）→ 報告書に記録として残る

設計原則：戦闘システムは「勝敗判定機」ではなく「段階的な結末を生成する装置」。出力は勝敗ではなく「4段階のどこに着地したか」。問いは「HPをどう管理するか」ではなく「何を入力に4段階のどれを出力するか」。

段階対応表（緊張度5段階と一致）：

- 軽：無傷で切り抜け → 肝を冷やしたが全員無事 → ロストなし
- 中：負傷 → 傷を負ったが隊商は守った → ロストなし（傷は記録に残る）
- 重：離脱・撤退 → 荷を一部失い撤退 → ロストなし（布石）
- 致命：ロスト → ○○は帰らなかった → ロストあり（無理をさせた時のみ）

# 支給品の段階開放（学習曲線）

- 隊商護衛達成までは支給品をつけられない（できることを初めは狭める）
- 初期につけられるのは2択のみ：包帯（守り）と煙幕（回避）
- この2択が戦闘3分岐と直接対応。包帯=正面突破の保険、煙幕=戦闘回避。支給品が戦術の意思表示になる
- 隊商護衛達成後、その商人からいつでも支給品を変えられる形に開放
- 開放される最初の1つは携帯食/携帯鍋を推奨（道中の消耗をやわらげる=全員無事に連れ帰る保険）。守り/回避/継戦維持の三竦みになる
- 注：MVPの掴みでは2択のままにする。三つ目を最初から見せると選択が濁る

# 掴みの全体フロー（隊商護衛〜捜索）

【隊商護衛】支給品は包帯/煙幕の2択のみ

- ①強行突破：戦闘寄り2名以上 + 包帯 → 負傷ありで完遂
- ②戦線離脱回避：煙幕支給（+斥候で確率up）→ 回避して完遂
- ③失敗：戦闘寄り0名 かつ 煙幕なし → 隊商行方不明・冒険者重傷/行方不明

【緊急捜索】③の後に張り出される

- 回復待ち + 適切な編成が要る
- 成功 → 救出・売買解禁（初回は割高→信頼で通常価格）
- 失敗 → 最後のチャンスへ

【最後のチャンス】最善策が明示される

- 最善策に従う → 救出成功・売買解禁（割高スタート）
- あえて不適切編成 → キャラロスト（エルシー除く）+ 信頼値大幅減、依頼は辛勝で前進

設計思想：護衛達成までロスト不可 → 達成後は「予兆→捜索→最後のチャンス」の3段階を踏んで初めてロスト。理不尽ロストは無し、段階を踏む、無理させた時だけ、を隙間なく満たす。

# 確定事項

- 掴みの依頼は隊商護衛（ドラマ型）
- 初期支給品は包帯・煙幕の2択のみ、達成後に段階開放
- 隊商護衛達成までロスト不可
- 戦闘3分岐（強行突破/離脱回避/失敗）
- 失敗条件は「戦闘寄り0名 かつ 煙幕なし」のみ
- ②回避成功率は斥候系で上昇（ミナ大/ロウ中/エルシー微）
- 失敗→緊急捜索→最後のチャンスの3段階
- キャラロストはエルシー除外
- 捜索成功の売買は初回割高→信頼で通常価格
- 捻くれプレイヤー（最善策を無視）はロスト+信頼値大幅減、依頼は辛勝で前進
- 新しい軸「信頼値（受付嬢・冒険者）」が発生。完成形の第3層への伏線

# 追記（2026-07-10 続き）：戦闘の時間軸と離脱適性

## 撤退判断フェーズ（1回制とラウンド制の折衷）

会敵時に第1判断、ラウンド3開始時に第2判断、以降は決着まで見届ける。

```
会敵（エンカウント）
  └─【第1判断】各冒険者が撤退判断
        ├─ 過半数が撤退 → 離脱処理（煙幕あり=続行 / なし=放棄で逃げ帰る）
        └─ 過半数が残る → 交戦へ
              │ ラウンド1〜2
        【第2判断】ラウンド3開始時に再度撤退判断
              ├─ 過半数が撤退 → 離脱処理（それまでの被害を反映）
              └─ 過半数が残る → 決着まで（勝利 or 敗北）
```

- 各冒険者が戦況を見て撤退判断。斥候・慎重・臆病は早い、豪胆は遅い。
- パーティの過半数が撤退判断で離脱（4人→3人、3人→2人、2人→2人）。
- エルシーは頭数に数えず群れの判断に従う。かつパーティ全体の撤退判断をやや早める（危険を先に察知して吠える）。
- 負傷の重さは「どこまで粘ったか」で自動的に決まる（第1で退けば無傷離脱、第2まで粘れば負傷）。

## 煙幕の二重効果

1. 各人の撤退判断に +30% バフ（退きやすくする）
2. 撤退成立時、戦闘スキップで先へ進める（依頼続行）。ただし効かない敵もいる（MVPでは効く固定、敵側に煙幕耐性フラグを将来持たせる）
- 煙幕なしで撤退＝依頼放棄で逃げ帰る。報酬なしだが「被害ゼロ＋そこまでの情報」が実質報酬。

## 敗北時の分岐（エルシーの有無）

決着まで見届けて敗北した場合：

| エルシー | 帰結 | ギルドへの伝わり方 | 次の展開 |
| --- | --- | --- | --- |
| あり | 人間は全員行方不明でもエルシーだけは必ず帰還 | エルシーが戻り状況が伝わる | 緊急捜索任務が発生 |
| なし | 全員行方不明に寄る | 帰還時刻超過→「何かあった」 | 時間経過で緊急捜索任務が発生 |
- エルシーは4kgの小型犬（パピヨン）なので担げない。役割は「運ぶ」ではなく「囮になって逃げ道を作る」。囮ログ発動、自身は身軽に必ず生還。

## 離脱適性（敗北時の 重傷帰還 / 行方不明 の振り分け）

土台は job（役割）で決める。既存コードが既に adv.job / adv.personality で分岐しているため、新規データ不要で組める。「戦闘の離脱適性」と「報告書ログの語彙」が同じ job 軸から出るので、結果とログが自然に一致する。

重傷で帰還できる確率（叩き台。後で調整前提）：

| job | 帰還確率 | 根拠 |
| --- | --- | --- |
| 斥候（ミナ） | 80% | 逃走・追跡のプロ |
| 見習い盾役（ロウ） | 65% | 退路・帰還が得意 |
| 薬草師（エルネ） | 60% | 自他の手当てで生存寄り |
| 戦士（ガッド） | 35% | 殿を務めて逃げ遅れる |

補正（すべて叩き台）：

- personality: 慎重 +10% / 豪胆（勇猛）−10%
- エルシー同伴: パーティ全員 +15%（囮ログ発動）
- エルシー自身: 常に帰還（100%）

例：エルシー同伴でガッド（戦士・豪胆）敗北 → 35 − 10 + 15 = 40% で重傷帰還、60% で行方不明。エルシーなしなら 25%。「一番強い戦士が真っ先に消える」ドラマが数値に出る。

## この追記での確定事項

- 戦闘の時間軸＝会敵時＋ラウンド3の2回判断、以降決着まで
- 撤退は過半数判断で成立、エルシーは頭数外＋全体を早める
- 煙幕＝撤退+30%＆スキップ続行（効かない敵は将来）
- 敗北時はエルシーの有無で「情報が伝わるか」が分岐、どちらも捜索依頼へ合流
- 離脱適性は job ベース＋personality微補正＋エルシー補正、数値は叩き台

## この追記での未決（次に詰める）

# 追記（2026-07-11）：戦闘内部値の初期方針（Claude Codeとのディレクター相談セッション）

前回追記「戦闘の時間軸と離脱適性」の未決事項のうち、以下4点の方向性が決まった。数値の中身（HP初期値式・ダメージ算出式・多数決のスコア合成の重み）はまだ未決で、次回セッションで詰める。

## 決定事項

### 戦況値の算出式

- パーティの `combat`（育成stats）の合算に、`weapon.power`（攻撃）/ `weapon.guard`（防御）を加算する式にする。
- 装備選びが戦況値に直接効くことで、支給品（包帯=守り／煙幕=回避）の意味付けとも自然に噛み合う。
- 具体的な加重・係数は未決。

### job / personality別の撤退しきい値

- job基礎値＋personality加算の方針（前回案どおり）。
- personalityは今後も種類を追加していく前提のため、`app.js` 内のハードコードswitch（`adv.personality === "慎重"` 等）ではなく、personality→補正値のテーブル参照へ設計変更する。
- ロウの「我慢強い」は、豪胆（ガッド）と同じ -10% 補正で扱う。

### 第1判断・第2判断のしきい値差

- Notion案のB（消耗を反映）とC（状況で判断が変わる）を組み合わせる方針に決定。
    - B：冒険者は個人ごとにHPを持つ（パーティ1プールではなく個人管理）。パーティ側HP対敵HPの数値比較を判断材料の一つにする。
    - C：状況補正。効果的なアイテムを持っていると退きにくくなる／敵HPが閾値（例：20%）を切ったら「ここで決める」方向の補正が入る。
    - B・Cを合算したスコアを冒険者ごとに算出し、各自の撤退可否判定を多数決で集約する。

### 「効果的なアイテム」の定義元

- 依頼データ（quest）側に新規フィールドを追加して持たせる方針。既存の `canUseItemInQuest()`（依頼への文脈適合判定）とは別系統のデータになる。

## 次回に持ち越す未決事項

- 冒険者個人HPの初期値をどう算出するか（`combat`から算出／固定値など）
- 敵の脅威度・HPを依頼データにどう持たせるか（新規フィールド設計）
- 1ラウンドごとの与ダメージ・被ダメージの算出式、被ダメージを誰が受けるか（戦闘担当1人に集中／分散）
- B（HP比較）とC（状況補正）を1スコアに合成する際の重み付け、多数決の合否ライン

個人HPの採用により、このシステムは単なる係数調整ではなく新規サブシステムになる見込み。実装は内部値確定後、`quest_evening_market_escort` を土台にした隊商護衛依頼の実装タスクとあわせて着手する（NEXT_[TASKS.md](http://TASKS.md) 参照）。

# 追記（2026-07-12）：戦闘内部値・残り4論点の決定

前回追記（2026-07-11）で持ち越した未決4点をすべて決定した。数値はすべて叩き台で、実装後の手触りで調整する前提。

## 決定事項

### 個人HPの初期値：job別基礎値

- 叩き台：戦士120 / 見習い盾役110 / 斥候90 / 薬草師80
- エルシーはHP管理の対象外（被弾せず、常に帰還する既存確定と整合）

### 敵データ：data-enemies.js を新設（マスターデータ化）

- 最小スキーマ：`id / name / hp / threat` の4項目のみ。依頼側は enemyId で参照する
- 採用理由：既存の data-adventurers / data-items / data-quests のマスターデータ分離パターンと一致する。いきもの図鑑（ゲーム第2層）との将来連携が自然にできる。隊商護衛以降すぐ敵が3体以上になるため、後からの移行コストを払うより最初から分離する
- 煙幕耐性フラグ・敵ギミックは将来の拡張枠（今回のスキーマには入れない）

### 被ダメージ配分：前衛集中型の重み分散

- 叩き台：前衛60%、残り40%を他の人間メンバーで等分。エルシーは0%
- 前衛の決定はjob順（戦士＞見習い盾役＞斥候＞薬草師）、同職の場合は courage の高い方
- 「殿を務めて逃げ遅れる戦士」という離脱適性の物語と、HPの減り方が一致する設計

### ヘイト値：今は作らない（将来拡張候補として保留）

- 前衛選定ルール自体が実質的な簡易ヘイト順として機能する。「前衛＝注目役」から「敵の注意を引きつけた」系のログを出す
- エルシーの「気を引く」は、既に確定している敗北時の囮ログ（囮になり逃げ道を作る、自身は必ず生還）の枠で表現する
- 数値としてのヘイトシステムは、HP・戦況値・撤退スコアの調整が落ち着いてから検討。一気に数値レイヤーを増やして調整不能になるのを避ける

### 合成式：加算型

- 個人撤退スコア ＝ 戦況スコア（味方HP計と敵HPの比較由来）＋ 状況補正の合計
- これを各自のしきい値（job基礎値＋personality補正）と比較し、超えた者が「撤退したい」に票を入れ、過半数で離脱成立（既存確定どおり）
- 煙幕の+30%等、既定の叩き台数値をそのまま足し引きできるため調整が直感的

## これで戦闘内部値の設計論点はすべてクローズ

- NEXT_[TASKS.md](http://TASKS.md) の「戦闘内部値の確定 [人間]」は設計判断としては完了。残るのは実装時の具体数値（戦況スコアの式、しきい値の絶対値）の叩き台設定と調整のみ
- 次のアクション候補：①隊商護衛依頼の実装 [AI可] の着手計画（戦闘3分岐・支給品制限・捜索チェーン込み）、②CURRENT_[SPEC.md](http://SPEC.md) の戦闘システム節への今回決定分の反映

# 追記（2026-07-14）：戦闘シーンの見せ方＝案B「交戦記録ブロック型」に決定

「ダメージ表記が見たい／そこだけRPGにしたい」という要望と旧方針（被ダメは数値非表示・ログ中心）の折り合いをディレクター相談で確定した。

## 決定事項

### 見せ方＝案B：交戦記録ブロック型

- 報告書ログ（report.logs）の中に、交戦部分だけ罫線で区切られた「交戦記録」ブロックが現れる形式。既存構造のまま、専用画面は作らない。
- ハラハラの主軸は「開封の瞬間」（開封前は数字が一切見えない）。数値は緊張を作る道具ではなく、事後検証（なぜ深手を負ったかを数字で追える）の道具と位置づける。
- 世界内の理屈：「ギルド規定で交戦時は数値記録を残すことになっている」。記録係は戦闘を見るのではなく、添付された交戦記録票を読む。書体・罫線を本文と変えて公文書感を出す。

### 表示するもの／しないもの

- 表示する：与ダメ数値、被ダメ数値（交戦記録ブロック内に限る）、ラウンド番号、撤退判断の結果（文章）、冒険者の状態語（健在／手負い／深手／戦闘不能）
- 表示しない：HP残量数値、HPバー、敵HP残量、命中率・回避率

### 旧方針の改訂

- 「被ダメージは数値より負傷・疲労・帰還後の様子で表現する」→「被ダメ数値は交戦記録ブロック内に限り表示可。HPは状態語で段階表示」に改訂。
- 「与ダメは表示してもよい」「命中率・回避率は原則入れない」「ログ中心の軽量交戦フェーズ」は維持。

### エルシーの扱い

- 交戦記録ブロックのダメージ行（与・被とも）には一切登場しない。
- 撤退判断まわりの文章行（例：「エルシーが低く唸り、一行の判断を早めた」）には登場してよい。

### 開封前の予感演出（小ネタ・採用）

- 報告書一覧に「交戦記録 添付あり」のバッジだけ先に見せる。中身は開封まで不明。最小差分で追加可能。

## 却下した案

- 案A（与ダメのみ数値）：旧方針改訂不要で最軽量だが、「そこだけRPGにしたい」の温度に届かない。数字が片側だけだと事後検証もできない。
- 案C（フルRPG窓：HP数値・ラウンド送り）：「記録を読む」体験が「戦闘を見る」に変質し、開封前ハラハラも薄まる。モックの範囲を超える実装過重。

1. スライス1：simulateBattle にラウンドのイベント列（与被ダメ・状態遷移・撤退判断）を吐かせる
2. スライス2：report.logs 内で交戦記録ブロックとして地味に描画する
- 前提：2026-07-12までに確定済みの戦闘内部値設計（個人HP job別基礎値／前衛60%配分／撤退2回制／加算型合成式／data-enemies.js）をそのまま使う。この決定はそれらの「出力の解像度」を定めたもの。

# 確定（2026-07-14）：状態語の遷移閾値（4段階）

状態語は **健在 / 手負い / 深手 / 戦闘不能** の4段階とする（実装スライス1で確定・2026-07-14）。

- **健在 → 手負い：個人HP 70%以下**
- **手負い → 深手：個人HP 35%以下**
- **深手 → 戦闘不能：個人HP 0（downed）**
- 「戦闘不能」を第4語として追加。理由：深手（まだ戦えている）と戦闘不能（倒れて動けない）はプレイヤーへの意味が全く違い、同じ語だと4段階結末（軽傷/負傷/離脱/失敗）との対応が読めなくなるため分離する。
- job別HP基礎値に当てはめた場合：
    - ガッド（戦士 120）：84で手負い / 42で深手
    - ロウ（盾役 110）：77で手負い / 38で深手
    - ミナ（斥候 90）：63で手負い / 31で深手
    - エルネ（薬草師 80）：56で手負い / 28で深手
- エルシーはHP管理外のため状態語なし。
- 前衛60%集中の被ダメ配分により、前衛は早めに手負いへ入り、後衛は無傷で終わることが多くなる想定。**これは意図通り**（前衛が身体を張っている感じが数字に出る）。
- 叩き台としての確定。プレイでの手触りを見て調整する余地あり。

# 改訂（2026-07-14）：案B「交戦記録ブロック型」を破棄 → 案D「戦闘ドラマログ型」へ

案Bの見た目叩き台をレビューした結果、**方向性が誤りだったと判断し、破棄する**。

## 案Bの何が間違っていたか

- 罫線で区切った「別紙」は、本文から**浮く**。作者が求めていたのは分離ではなく**融合**だった。
- ラウンド番号は「システムの都合」であり、**記録係が報告書に書くはずがない**。世界内の理屈でもむしろ不自然。
- 決定的に、**「誰が何をしたか」の動詞がない**。「ミナ→敵 7」には物語がないが、「ミナは短弓から矢を放った。野盗の左肩に命中した！」にはある。
- 記録係トーンを守ることに気を取られ、**トーンを守るために面白さを捨てていた**。本末転倒。

## 案D：戦闘ドラマログ型（確定）

戦闘を「交戦記録票」として表示するのではなく、**戦闘そのものを報告書の文体で語らせる**。数値は表の項目ではなく、**文章の中に括弧で刺さる**。

### 形式

- **ラウンドは内部保持のみ。表に出さない。**
- 1行 = 1アクション。**動作の描写 ＋ 結果 ＋ 括弧内の数値**。
- 数値は文章の中に括弧で入る。
- 回復・アイテム消費も同じ形式で出す。
- トドメには専用の締め文を用意する。
- **戦闘内にドラマが必ず必要**（単なる数値の羅列にしない）。

### 出力例（作者提示）

- 「ロウは立ちはだかり野盗からの攻撃を受け止めたが、衝撃は殺しきれなかった（ロウに-2ダメージ）」
- 「ミナは短弓から矢を放った。野盗の左肩に命中した！（野盗に-12ダメージ！）」
- 「ガッドはよろけた拍子に、野盗からの斬撃をまともに受けてしまった！（-8ダメージ！）」
- 「ロウは突撃し、野盗を弾き飛ばした！（野盗に-4ダメージ！）」
- 「エルネはガッドに応急処置を施した（ガッドは10回復）（包帯消費：1）」
- 「ミナは矢を放ち、それが最後の一撃になった。野盗を退けた。」

### 既存ログの扱い（重要な変更）

- **既存の戦闘描写の文章ログは、この案Dで置き換える。**
- 理由：既存の戦闘描写ログは、ここに行き着くまでの**仮置き**だった（作者確認済み）。
- 戦闘以外のログ（出発・到着・結果・余韻）はそのまま残す。

### 案Bから引き継ぐもの

- 与ダメ・被ダメの数値表示（旧方針の「被ダメは数値非表示」の改訂は維持）
- 状態語4段階（健在／手負い／深手／戦闘不能、閾値70%/35%/0）※ただし表示形式は文章に溶かす
- HP残量数値・HPバー・命中率は表示しない

# 追記（2026-07-14）：回復モデル化の設計方針（スライス5）

戦闘に回復を導入する。これは **support stat を初めて戦闘計算に接続する** という設計上の節目。

## 決定事項

### 回復役の決まり方

- **support が最も高い人間の冒険者**が回復役になる（エルネ固定ではない。support値で決まる）。
- エルネはsupportが高い設計なので実質的に回復役になるが、ロジックはstat依存。

### 回復の発動条件（B案：条件発動）

- 誰かが「手負い／深手」になった時に回復が発動する（毎ラウンド自動ではない）。
- 「深手のガッドに駆け寄る」という因果がドラマログに出る形にする。

### 包帯の扱い

- **包帯がないと回復は起きない。**（素手回復なし）
- 回復には包帯を1個消費する。
- 包帯が尽きたら回復できない。
- → 「包帯を持たせるか」という出撃前の選択が、戦闘結果に影響する最初の例になる。

### エルシーと包帯

- **エルシーは包帯の「運び手」。** エルシーが持つ包帯を、support が高い人間が優先的に使う。
- エルシーは道具を使えない（人間行動禁止）ため、運ぶだけ。使うのは人間。
- これによりエルシーの「戦闘主力ではないが役に立つ」性質と噛み合う。

### 回復のタイミング

- 戦闘中（手負い・深手への遷移時）
- 戦闘後（帰還前の手当て）も候補

## 設計上の位置づけ（重要）

- 現在の simulateBattle は support stat を戦闘計算に一切使っていない。回復導入は **support を戦闘に繋ぐ最初の一歩**。
- 同様に将来、survival を撤退判断に、combat をダメージ計算に繋ぐ話になる。
- ただし**今回は support だけを回復という形で繋ぐ**。他statへの波及は今回やらない（限定した接続に留める）。
- 注意：battleStats（maxHp/strength/magic/stamina/defense）は将来構想で未実装。現在の戦闘は job別HP基礎値で動いている。support接続は battleStats とは独立した最小の接続とする。

## バランスへの影響

- 回復が入ると「supportの高い人間＋包帯」の編成は負けにくくなる。これは**望ましい**（編成の選択が結果を変える）。
- 4段階結末の閾値を回復込みで再調整する必要があるかは、実装後にシミュレーションで確認する。

## 別スライスに切る（今回やらない）

- **「終わりの見えない戦い」の表現**：長期戦・泥沼。決着がつかないまま複数ラウンド続く敵。撤退判断を増やすより「ラウンド上限を超えても倒れない敵」を作る方向で別途検討。simulateBattle のループ構造に関わるため、回復とは別スライス。

# 重大な設計決定（2026-07-14）：HP/攻撃を stat 由来にする（方向2）

## 背景：HP定義が3つ並立していた問題

Bの整理に着手した結果、HP/攻撃力の定義が **3つ乖離して並立** していたことが判明した。

1. 職業性格前職_数値表_v0.1：能力5種＋基礎HP20＋補正（旧世代設計。能力名も現行と違う）
2. 開発引継ぎメモの battleStats（maxHp/strength/magic/stamina/defense。未実装）
3. 実装の simulateBattle：job別HP（戦士120/盾役110/斥候90/薬草師80）。この数字に設計根拠なし（実装時の決め打ち）

→ 「設計上のHP（約30）」と「実装のHP（120）」が桁違いで、どれも互いに繋がっていなかった。

## 決定：方向2（設計を正とし、HPを stat から計算する）

実装のjob別HP決め打ちをやめ、**HP・攻撃を stat の関数にする**。support接続（スライス5）で「statを戦闘に繋ぐ」パターンが動いた実績を、HP/攻撃に横展開する。

### 論点1・2：何から計算するか（確定）

- **HP = survival 由来 ＋ job補正。** survival＝生存・悪条件対応・生還力。HPの器と意味が一致。
- **攻撃（与ダメ）= combat 由来。** combatが高い＝よく削る。ガッドが強い理由が数字で裏付く。

### 論点4a：スケール（確定）

- **実装の現行スケール（HP80〜120、ダメージ15前後）を維持する。**
- stat からそのスケールに変換する係数を噛ませる（例：HP = 基礎 + survival×係数 + job補正）。
- 見た目・手触りは変わらず、裏側だけ stat 駆動になる。ドラマログの現行の温度を壊さない。

### 論点3：被ダメ配分（今回は据え置き・第二弾で扱う）

- **今回は前衛60%集中・job順のまま据え置く。**
- 理由：HP・攻撃・配分を一度に全部 stat 化すると、どの stat が効きすぎか切り分けられなくなる。まずHPと攻撃だけ stat 化してシミュレーションで確認し、安定してから配分に手を付ける（support接続を単独スライスにしたのと同じ段階分け）。

## 段階分け

- **方向2・第一弾（次のスライス）**：HP=survival由来、攻撃=combat由来。スケール維持。配分は据え置き。
- **方向2・第二弾（保留）**：被ダメ配分の stat 駆動化。
    - 構想：**survival の 1/10 だけ被弾率%を足す弱い補正**くらい。survival高い＝前で耐える役回りが増える。
    - 課題：ミナ（斥候）が survival 高いと前に出て狙われる矛盾が出る。**job の前衛適性と組み合わせて調整**する（斥候はjob補正で被弾率が下がる、など）。
    - 弱い補正に留めることで、survival が HP と配分の両方に効く「二重取り」のリスクを抑える。

## 却下した方向

- 方向1（実装の120系を正とし、設計を実装に合わせる）：最小コストだが、数値表の思想（能力値がすべてを決める）を捨てることになる。将来のレベルアップ（statが変動すると戦闘も変わる）と噛み合わせるには、stat由来にしておく方が良いと判断。

## 注意

- この変更は simulateBattle の HP・与ダメ計算の書き換えを伴う。バランスが変わるので、シミュレーションで回復なし/ありと同様に「変更前/後」の結果分布を比較する。
- スライス5で入れた回復（support由来・固定15）との相互作用も確認する。HPがsurvival由来になると、回復15の相対的な重みが変わる可能性がある。
