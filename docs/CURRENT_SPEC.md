## 基本ループ

1. 依頼掲示板を見る
2. 時間帯・天候を確認する
3. 依頼を選ぶ
4. 冒険者を1〜4人選ぶ
5. 冒険者ごとに支給品を選ぶ
6. 遠征へ送り出す
7. 帰還後の報告書を読む
8. 今回のハイライト・報告メモ・生態目録を確認する

### 同時遠征は2本まで（2026-09-20・EX-138）

- ★ **遠征は同時に2本まで出せます**（`MAX_CONCURRENT_EXPEDITIONS`）。上限は**本数**で持ちます——人数で持つと、工程の疲労（少人数ほど重い）と**二重のブレーキ**になるためです。
- ★ **同じ依頼を2本同時には出せません。** 出ている依頼は**掲示板から下ります**（クールタイムは帰ってきてから効くので、出ている間は別の規則で下ろす必要があります）。
- ★ **捜索チェーンに関わる依頼（隊商護衛・捜索2件）は同時1本まで**です。旗は依頼データが持ちます（`chainSlot`）。チェーンは物語の一本道で、2本並ぶと「どの隊商の話か」が報告書から読めなくなるためです。
- ★ **クールタイムと再出現は今までどおり「報告書の本数」で数えます。** 2本同時に帰ると一度に2進む＝掲示板が速く回るのは、**同時遠征の利益として受け入れています**。
- ★ **暦と行方不明の時計は「遠征が1本でも走っている区間」で進みます**（0本→1本で起点、1本→0本で確定）。⚠️ 完了のたびに所要日数を足すと、**重なった2本を二重に数えます**（30分＋30分＋60分を並行させると暦は2日進みますが、実際に過ぎたのは1日ぶんです）。
- ★ **「その依頼の初回か」は出発時に確定して遠征データへ書きます**（`firstRunOfQuest`）。帰還時に報告書を数える形だと、出撃中の回が勘定に入らないためです（例外は例外としてデータに書く、の流儀）。
- ★ **帰還の通知は行列です。** 同時に2本帰っても、片方の「帰還を確認する」が消えません（1件ずつ確認できます）。
- ★ **出発の直前に編成の `status` を見直します。** これまでガードは画面側（編成カードの無効化）だけでした。
- ★ **保存は `schemaVersion` を上げずに移し替えます**（単数 `expedition` → 配列 `expeditions`／`activeResultReportId` → 行列）。遠征中のまま保存された旧セーブも、**そのまま続きから畳めます**。

### 報告書の乱数は出発時に決まる（2026-09-20・EX-138）

- ★ **報告書の中身を決める乱数は、出発した瞬間に確定した種（`expedition.seed`）だけから作ります。** 帰還がいつでも、その間に何が起きても、**同じ遠征からは同じ報告書が出ます**。
- ⚠️ **以前は手元の報告書の本数と出発回数を種に混ぜていました**（`totalExpeditions * 37 + reports.length * 101`）。そのため**同じ遠征でも、別の遠征が1本帰っただけ・2本目を出発させただけで本文が変わりました**（2026-09-20・EX-137 の実測）。
- ★ これを直した理由は2つです。**①検証の前提**——「同じ種なら不一致0」という比較が、手元の状態に依存していては成り立ちません（`tools/sweep.js` は毎回カウンタを0に戻して測っていました）。**②同時遠征の前提**——複数の遠征を同時に走らせると、同じ瞬間に2本畳んだときの**処理順で本文が入れ替わります**。
- 在席ログ・掛け合い・成長ログの3本は**以前からこの形**でした（`seed + 991` / `+ 553` / `+ 317`）。今回そこへ揃えただけで、**新しい仕組みは足していません**。

## 依頼

**どの依頼が存在するかの正本は `data-quests.js`。この文書は一覧を持ちません。**

一覧は「事実」であってコードに実在するため、文書に写すと複製になります。依頼が1件増えるたびに手で追従が必要になり、追従を忘れた瞬間に仕様の正本が旧値を配る文書に変わります（実際に13件のまま4件分腐りました）。この文書が持つのは、**その配置を生んだ判断＝規則**だけです。

一覧が必要になったら、そのつど実装から作り直します。

```bash
node scripts/gen-quest-table.js
```

出力の先頭には**生成日時**と**「これは生成物であって正本ではない」**の2行が自動で付きます。この2行がない一覧を貼らないでください（貼った瞬間に旧値を配る文書になります）。

### 結末の候補と結末文はデータ側にある（更新: 2026-08-01）

- **その依頼にどんな結末がありうるか**は `data-quests.js` の `outcomes` が持つ。完遂（`full`）／部分（`partial`）／未達（`fail`）の3段階で、**工程エンジンの結果の段階と同じ形**。
  - ★ これで**結末と段階の対応表が1つになった**。`app.js` の `GROWTH_TIER_BY_RESULT` は依頼データから作られる（成長用と判定用で2つ持たない）。**新しい依頼を足しても登録漏れが起きない。**
  - `fail` が空の依頼は、未達のとき共通の「引き返し」に落ちる。
  - 並び順は移行前のコードのまま。同じ乱数で同じ結末が出る（移行時に不一致0を確認した根拠）。
- **結末の文面**は `data-outcomes.js` が持つ。依頼ID → 結末の鍵 → `result` / `summary` / `line` / `after` / `history`。
- ★ **データに書けるのは名札と列挙だけで、式は書かない。** 差し込みは `{一行}` `{斥候}` などの名札、条件は `app.js` の `OUTCOME_CONDITIONS` にある名前だけ。
  - 理由：条件式を JSON に持ち込むと**JSON がコードになる**。データに出す目的（移行しやすさとメンテナンス性）がどちらも消える。
  - **描写（エルシー・ハイライト・掛け合い）はコードに残す。** 人数・性格・天候の条件に強く依存していて、出すと文章が書きにくくなる。体験の中心が報告書なので、書きにくさは高い代償。
- **結末が工程も戦闘も見ない例外**は、依頼データの `outcomeOverride` で表す（条件の列挙 → 結末、当たらなければ `default`）。隊商捜索チェーン2件の**2件**（★ 2026-09-13 に夜道の灯りが外れました＝v2 は通常の戦闘計算に乗ります）。
  - ★ 目的は**例外であることが `data-quests.js` を見て分かる状態にすること**。移行前は依頼IDのハードコードで、データ側から例外だと読めなかった。

### 判定用語彙（`data-vocab.js`・2026-08-06・EX-061）

★ **`tags` とは別の表**です。**行為（How）× 対象（What）の2軸**で、**冒険者・支給品・工程の3組が1つの表を共有**します。

- **行為14語（主）**：運ぶ／察する／**確かめる**／伝える／前に立つ／攻める／進む／手当て／記録／留める／整える／火と食／**採る／離れる**（〈採る〉〈離れる〉は 2026-08-18・EX-063 追加。★〈離れる〉は〈退く〉ではない——撤退は「荷物を置いてくること」であり逃走ではないので、敗北の語感が薄い語を採った）
- ★ **〈確かめる〉は〈察する〉から割りました**（2026-09-12・EX-088）。**効く能力が違うためです**——〈察する〉＝**痕跡から読み取る**（足跡・轍・匂い。斥候の仕事）／〈確かめる〉＝**物が壊れていないか点検する**（ゆるみ・傷み。手先や経験の仕事）。

#### ★ 工程と、本文の作業行は別物です（2026-09-12・EX-080 の裁定C）

★ **報告書の作業行は、工程エンジンの工程と対応しません。対応させる必要もありません。**
同じ出来事を二度書いているのではなく、**別々のものとして書かれてきた**という判断です（同じ問いを立て直さないために書いておきます）。

- **担い手を決める仕組みと、本文の主語を決める仕組みは別**です。担い手＝語彙で絞って育成値が最大の者／本文の作業行の主語＝職・気質・前職（`findByTrait`）／滞りと手当ての行＝人間からランダムな1人／支給品の行＝所持者。**4つが独立して人を選びます。**

## 装備と支給品の線引き（更新: 2026-07-31）

| | 誰が決めるか | 何のためにあるか |
|---|---|---|
| **装備**（武器・アクセサリー） | **冒険者本人**が報酬で勝手に揃える | **冒険者の個性を出す** |
| **支給品**（包帯・煙幕など） | **プレイヤー** | 今回の遠征への判断 |

この線引きは、既存の設計を成立させる前提です。**「後輩に剣を託す」将来フック**も、**遺品**（捜索チェーンの遺体捜索→遺品）も、**装備が本人のものでなければ成立しません**。ギルドの備品を託しても遺品にはなりません。

- guard / power を **UI に出すかは未決**。装備で決まるならプレイヤーが判断できる情報になるので見せる価値はありますが、数値をそのまま出すかは別問題（他の stat も UI に出ていないため、「打撃に強い」のような装備の説明の形の方が揃う）。

## エルシー仕様

エルシーは `species: "dog"` の特別なギルド犬です。

- `special: true` は内部判定用に残す
- UI上で「特別」バッジは強調しない
- `canSolo: false`
- エルシー単独では出撃不可
- ★ **育成値は探索特化**（2026-08-06・EX-057）。**戦闘0／交渉0／支援0／調査10（据え置き）／探索32／生存30**で、**探索と生存は人間の一位（ミナ28・ロウ25）を抜きます**。調査を上げないのは**犬にできない行為の担い手になる圧を上げないため**。★ **戦闘0は与ダメに波及しません**——`simulateBattle` は冒頭で人間だけを取り出しており、`fighters` も `computeBattleForecast` もエルシーを含みません（効くのは `hasElsie` の旗＝撤退の成否と結末だけ）。
- 人間用ログ候補には混ぜない
- エルシーは犬用ログだけに出す
- 人間1人＋エルシーは、完全ソロでも完全複数人でもない中間扱い

エルシーにさせない行動：

- 記録する
- 説明する
- 声をかける
- 読む
- 修理する
- 納品書を確認する
- 拓本を取る
- 会話する

★ **犬が担い手になってよいのは、その育成値に犬固有の文面があるときだけです**（2026-09-11・EX-074 で明確になった線）。
「効いた瞬間」の文は**育成値（`statKey`）で選ばれる**ので、犬固有の文が無い育成値では**どの工程を担っても人間用の文が出ます**。
- `exploration` には犬固有の文があるので、**薬草包みの納品は犬が担い手でよい**（2026-08-18・EX-057 の裁定どおり）。
- `investigation` には犬固有の文が無いので、**古い石碑の拓本は依頼単位で犬を外しました**（`fieldworkHumanOnly: true`）。EX-074 の語彙フィルタで、犬だけが〈記録〉〈留める〉の語を持つ編成のときに犬が担い手になり、「エルシーは確認の順番を崩さず、書き損じのないまま終えた。」が出たためです（`scripts/check-elsie-actions.js` が違反1件として検出。宣言の追加で0件に戻した）。

★ **この禁止は工程エンジンの「担い手」にも効きます**（2026-08-06・EX-056）。担い手の名前は「効いた瞬間」や依頼専用の行の主語になるため、**犬が担い手になると上の行動を書いてしまいます**。依頼側の `humanOnly` 宣言で担い手から外し、**書き忘れは `scripts/check-elsie-actions.js` で洗います**（全依頼×全編成を回し、宣言のない工程で犬が担い手になったときに文面が上のリストに触れていないかを見る。DevTools に貼って `checkElsieActions()`）。

エルシーができる行動：

- 匂いを嗅ぐ
- 耳を立てる
- 吠える
- 低く唸る
- 足元を歩く
- 先に立ち止まる
- 振り返る
- そばにいる
- 伏せて待つ
- 袖口や裾をくわえる

  - ★ **一次情報として持つことと、画面に出すことは別**です（2026-09-18・EX-134）。ゲーム内日数は正本として持ち続け、暦の加算もそれを読みますが、**画面には出しません**。依頼を選ぶときに効くのは実時間だけで、ゲーム内時間は判断の役に立っていないためです。
  - ⚠️ 旧表示は「8分（実20秒）」の形で両方出していました。EX-133 で最初のクエストだけ実時間のみにしましたが、**例外が1件だけ残ると画面から理由が読めない**ので、EX-134 で全依頼に揃えました（`realDurationOnly` の旗は役目を終えて削除）。
  - ★ **帯の表の「ゲーム内」の列は持っている値で、画面には出していません**（2026-09-18・EX-134）。
- 遠征完了時に `worldState.daysPassed` へ所要日数を加算します（**画面表示は②-2で実装**）。
- `expedition.startTime` は絶対時刻なので、タブを閉じても実時間は進みます（「寝る前に出して朝読む」が成立）。

### 体験版モード（時間加速）

- 依頼掲示板の `🔧 時間加速` バーで `等倍 / 60倍 / 3600倍` を選びます。`state.demoSpeed` に保存され、リロードしても維持されます。
- `expedition.durationMs` には**素の値**を保存し、完了判定と進捗率の比較時に倍率を掛けます。**出発済みの遠征も加速できます。**
- Mock用の即帰還ボタンは**加速中のみ表示**します（等倍＝素の状態＝人に見せる状態）。

## 依頼の表示制御（更新: 2026-09-15・EX-102）

掲示板は **`buildBoardQuests` が組み立てます**（2026-09-15・EX-102）。手順は3つです。

1. **候補を絞る**：`!quest.hidden && isQuestUnlocked(quest, clearedQuestIds) && questBoardVisibility(quest, state.reports).visible`
2. **クールタイムで分ける**：一度でも行った依頼は `questCooldownState` が見ます。
   ★ **行ったら引っ込み、消化数1〜3で戻ります**（EX-049 の確定事項）。必要数は
   **何回目の実施か**で 1→2→3→1… と巡回し、経過は `state.reports` の添字（＝その回より新しい報告書の数）で測ります。
3. **並べて6枠で切る**：**未消化が先**で、**解放の浅い順**（同じ深さなら定義順）。
   余った枠を、クールタイムが明けた既消化で埋めます（**久しく行っていない順**・同点は定義順）。

- ★ **枠数とクールタイムの値はデータ側**（`data-quests.js` の `window.masterBoardRules`＝`slots: 6` ／ `cooldown: { min: 1, max: 3 }`）。
- ★ **緊急依頼（捜索チェーン）は枠の外**です。先頭に割り込むので、**カードは最大7枚**になります。
- ★ **抽選はしません。** 掲示板は操作のたびに描き直され、遠征中は毎秒走るので、
  乱数を引くと毎秒ちらつきます（EX-093 と同じ理由）。並び順は同じ状態なら必ず同じです。
- ★ **`state` を増やしていません。** 解放も消化も必要数も、すべて `state.reports` から毎回導きます。
- ⚠️ **クールタイムの「小休止」と「枠あふれ」は画面に理由を出しません**（EX-102 の裁定）。
  出すと毎回ずらずら並び、「忘れた頃に掲示板にある」という質感が消えます。
  1行を出すのは**再出現つきの依頼の待機中だけ**（下記）。
- ⚠️ **選択中の依頼が掲示板から消えたら選択を外します**（再出現の待機中／クールタイムの小休止／枠あふれの3つとも）。
- ★ **未消化が6枠を超える局面は実在します**（実測：到達可能な1,332状態を全列挙して**最大7件**）。
  そのとき落ちるのは**いちばん深い依頼**で、例えば消化10件の局面では「街道の外れを行く隊商の護衛」が枠から外れます。

### 再出現（`reappearAfterCount`）はクールタイムとは別物

- ★ **再出現**（2026-09-13・EX-093）。依頼データの宣言 `reappearAfterCount: { min, max }` を持つ依頼だけに効きます。★ **器はクールタイムと同じ「消化数」ですが、規則が逆向きです**——クールタイムは「行ったら引っ込み、また戻る」、再出現は「**倒すまで戻り、倒したら二度と出ない**」。両方を持つ依頼は、まず再出現で判定し、そこを通ったものだけクールタイムを見ます（厳しい側が勝ちます）。
  **倒していない間だけ掲示板に戻り、倒したら二度と出ません。** 倒したかどうかは結末の段ではなく
  `hiddenTags.battleOutcome === "victory"`（＝戦闘の事実）で見ます。間隔は**依頼の消化数**で測り、
  EX-049 で確定している「クールタイムは消化数1〜3」に合わせています（挑戦のたびに 1→2→3 と伸びます）。
  - ⚠️ `state.reports` は **unshift（新しいものが先頭）**です。ここを取り違えると
    「挑戦直後にすぐ戻り、以後は消化数と無関係に点滅する」という逆の挙動になります（初版が実際にそうでした）。
  - ⚠️ 必要数は**添字ではなく挑戦回数**から決めます。添字は報告書が増えるたびに動きます。
  - 旧セーブにある v1 の報告書は**挑戦に数えません**（`battleOutcome` も `daylightMiss` も持たないため）。
  - ★ **待機中のときだけ、掲示板の上部に1行出します**（2026-09-14・EX-095）：
    「{依頼名}の件は、まだ次の話が来ていない。」。**数字は出しません。**
    - **「解決済み」は出しません**——勝った回の結末文が既に言っているので、二度書かない。
    - **「戻ってきた」も出しません**——★ **忘れた頃に掲示板にあるのが設計7の質感**で、
      告知すると「イベント発生」になる。
    - `state` は1つも増やさず、毎回 `state.reports` から導きます。
**`hidden` と `unlockedBy` は別概念**です。

| フィールド | 意味 | 対象 |
| --- | --- | --- |
| `hidden: true` | **掲示板には永久に並ばない。** `state.searchChain` を見て先頭に割り込む専用経路 | 捜索チェーンの依頼 |
| `unlockedBy: "quest_xxx"` | **まだ出ていないだけ。** 指す依頼へ一度でも遠征していれば並ぶ | 初期公開以外の依頼 |
| `unlockedAfterCount: N` | **達成数で開く。** 行った依頼が N 種類あれば並ぶ（**どの依頼かは問わない**） | 廃屋の片付け（2026-08-06・EX-054） |

- ★ **`unlockedBy` と `unlockedAfterCount` は別の条件で、両方あるときは両方満たしたときだけ開きます**（AND）。数えるのは**行った依頼の種類数**なので、同じ依頼を2回行っても1件です。
- **解放判定は成否を問わない**（その依頼の報告書が1件でもあればよい）。失敗で行き止まりにすると「失敗も物語として進む」設計と矛盾するため。
- **解放状態のための state は持たない。** `state.reports` の `questId` から都度導出します（`schemaVersion` 据え置き）。★**将来「報告書を削除できる」ようにすると解放が巻き戻る**ので、そのときは見直しが必要です。

### 掲示板カードの項目（2026-09-18・EX-134）

- 出すのは**5項目で、依頼の分類によらず常に同じ**です：**分類／危険度／地域／所要時間／観察対象**。
- ★ **「危険度」は分類によらず1つの名前です**（EX-134）。以前は生活クエストだけ「作業負荷」と呼び、値を別色にしていましたが、**同じ `danger` の値を分類で呼び分ける意味がない**ので揃えました。色分けも外しています（値の段ではなく「生活かどうか」を色にしていて、すぐ上の「分類」の行と二重でした）。
- ★ **「観察対象」の行は、遭遇したあとだけ出ます**（2026-09-18・EX-135）。依頼を受ける前に「観察対象はなし」と書いてあると、**行く前から何がいるか分かっていること**になるためです。**掲示板は住民が貼った紙で、住民は何がいるかを知りません。**
  - 判定は `state.reports` から導きます（`state` は増やしません）。★ **遭遇の印は報告書の `observationNotes` が `null` でないこと**（2026-09-17・EX-117 で分けた区別をそのまま使います）。`null` ＝ 対象がいなかった回／`{ notes: [] }` ＝ 出会ったが記録票を持たせていなかった回で、**後者は遭遇に数えます**。
  - ★ **「行った」ではなく「遭遇した」で判定します。** 例：夜道の灯りは昼に行くと会えないので、その回の報告書があっても行は出ません。夜に会うと出ます。
  - ★ **観察対象を持たない依頼（「なし」）は、遭遇そのものが起きないので行が出ません**（全20件中15件）。★ これは規則をそのまま当てた結果で、例外は足していません。
  - ★ **反ミームの対象は遭遇後も出しません**（依頼データの `antiMemeticTarget`）。**記録されない存在**なので、**掲示板に残らないこと自体が性質の表現**になります。★ プレイヤーは**自分が遭遇したことすら掲示板からは読めません**。⚠️ **現時点で該当する依頼は0件**で、仕組みだけ置いてあります。
- 値が無いときに**項目ごと落とす分岐は、この観察対象の行だけ**です。他の4項目は常に出ます。
- ⚠️ **`danger` が何を表す値なのかは決まっていません**（未解決。2026-07-26「距離の情報を持たない」／2026-08-31「高危険なのに重症0%」）。★ **着手条件＝体験版の難度を詰めるとき、または「危険度を見ても判断できない」が実際に観測されたとき。**

### 解放ツリーの規則

**どの依頼が何で解放されるかの正本は `data-quests.js` の `unlockedBy`。この文書はツリーの全件表を持ちません**（一覧と同じ理由で腐るため）。実際のツリーは `node scripts/gen-quest-table.js` の「解放条件」列で確認します。

配置を決めているのは次の規則です。

- ★ **初期公開は最初のクエスト1件だけ**（2026-08-05・EX-053）。`quest_tavern_errand`「隣の酒場に買い出し」（★ **10秒**。2026-09-18・EX-133 に 20秒から短縮）。**クリアすると結婚式・夕市・夜道が開く**。
  - ★ **この依頼だけ、初回に限り未達（出直し）が出ません**（2026-08-06 裁定／2026-09-18・EX-131 で実装）。依頼データの `firstRunNeverFails` が立っている回のうち、**その依頼を一度も行っていないとき**だけ未達を完遂へ引き上げます。**2回目以降は通常の判定**に戻ります。★ **部分（寄り道）は初回でもそのまま出る**ので、結末の幅と担ぎ手の書き分けは失われません。⚠️ **負荷の数値では下げていません**——例外は例外としてデータに書く（`outcomeOverride` と同じ扱い）。
- ★ **廃屋の片付けは達成数2件で開きます**（2026-08-06・EX-054。`unlockedAfterCount: 2`）。**どのクエストを終えたかは問わない＝3回目に選べる**という条件を、特定の依頼に繋がずそのまま表しています。実測は 0件＝1件表示 ／ 1件＝4件 ／ 2件＝6件（ここで廃屋が出る）。道標は従来どおり廃屋の後ろです。

  - ★ **内訳を書いておきます**（2026-08-01。「4件で5時間＝1件75分」という読み違いが実際に起きたため）：酒場10秒 → 廃屋1分 → 道標30分 → 畑30分 → 納屋60分 ＝ **前提5件で約121.2分**、そこへ**護衛本体の180分**が乗って約301.2分。**5時間のうち60%は護衛1件**で、1件あたりが長いわけではありません。
  - ★ **所要時間は進行につれて伸びています**（深さ0の平均7.8分 → 1が30.0分 → 2が67.5分 → 4が150.0分）。「序盤は近場、遠くへ行くほど長い」は既に `durationBand` で表現されており、新しい仕組みは要りません。
- ~~初期公開は4件。増やさない~~ → **2026-08-05 に1件へ**（上記）。増やさない方針は変わらない
- 側枝は掲示板を賑やかにしますが**進行を塞ぎません**
- **帯順（距離）と解放順は一致しなくてよい。** コアコンセプト17章の「序盤は戦闘の供給を少なく」は**危険度の話**であって距離の話ではない

## 負傷の持続と回復（更新: 2026-07-29・第3段階）

負傷は依頼をまたいで残り、時間経過で自動的に回復します。**回復枠をプレイヤーに管理させません**（冒険者は自分で治療に行く）。

### 負傷の重さは「stage」ではなく「帰還時の個人HP率」で決まる

- 閾値は**既存の状態語をそのまま流用**します（`battleStatusWord`）。70%超＝負傷なし／35〜70%＝**軽症**／35%以下＝**重症**。新しい閾値を増やしません。
- ★ **結末（stage）は使いません。** stage は物語の重さであって負傷の深さではないためです。実測（2026-07-29）では3つの stage で帰還時HP率がほぼ同じで、特に **stage重＝撤退は HP が高い**。stage を境界にすると「撤退したら全員重症」になります。
- 負傷が付くのは**戦闘のある依頼**だけです。戦闘のない依頼では誰も負傷しません。
- **エルシーは負傷しません**（戦闘のHP管理外という既存仕様のまま）。

### 回復

- 回復にかかる実時間は `data-time.js` の `masterRecoveryTimes` が持ちます（**値はデータ側が正本**。ここには書きません）。**軽症は「ほぼ即また出せる」長さ**にします。連続で出せることを守るための受け皿です。
- **オフライン中も進みます。** 負傷した絶対時刻を保存し、現在時刻との差で判定します（依頼の `startTime` と同じ考え方）。素の値を保存し、体験版モードの倍率は比較時に掛けます。
- **残りは実時間だけで見せます。ゲーム内の日数へ換算しません**（暦を出さない方針のため）。

### 拒否

- **重症は本人が断ります。編成画面ではボタンを塞ぎません。** 選べるが、遠征開始で断られます（「命じれば行く。ただし重症なら断る」）。
- ただし**編成画面と名簿に状態バッジ（重さと残り時間）を出します**。見えているうえで強行したときだけ断られるので、無駄足になりません。
- **軽症は出せます。** 中程度で断ると実質全員が使えなくなるためです。

### 負傷は戦闘の開始HPに影響しない

毎回 `maxHp` から始まります。負傷が効くのは**出撃可否と回復待ちだけ**です。2026-07-29 に「戦闘の数値は触らない」が確定しており、開始HPを下げると確定済みのバランスが崩れるためです。

## 行方不明と死亡（2026-08-18・EX-070・実装済み）

冒険者を失いうる最初の経路です。★ **稀でよい（起きたときに重いことが本体）**。

### 発生（個人単位）

- **戦闘が敗北（`defeat`／`stalemate`）で終わったとき、戦闘不能（`downed`）のままの者だけ**が行方不明になります。勝利・撤退成立なら全員連れ帰ります（現行どおり）。
- ★ **エルシー同行時は発生しません**（全員連れ帰る。撤退保証と同じ層＝「深い失敗を浅くする犬」の延長）。エルシー自身も対象外です。
- ★ **致命（人間全員 downed）は当面対象外**＝現行の重症帰還のまま。報告者不在（誰が知らせるか）の文面設計が要るため、含めるかは実例が出てから再裁定。
- 対象は戦闘経路の3件すべて（畑・納屋・隊商護衛）。実測の発生率は**護衛×エルネ+ロウで 0.45%**、他の編成・依頼は0%（弱編成は段階1で引き返すため敗北自体が稀）。
- 報告書には「連れ帰れなかった」の行（仮置き1文・抽選なし）が出て、`hiddenTags.missingIds` に残ります。

### 時計（行動時間）

- ★ **発生時点では時計を動かしません。起点はプレイヤーが判明した時**（その報告書を開く・名簿を見る）。
- ★ **進むのは「進行中の遠征が存在する間」だけ**。遠征がなければ止まります（迷う時間はプレイヤーのもの。ただし仲間を働かせている間は世界の時間も進む、という形）。
- 判明時に別の遠征が進行中ならそこから、無ければ次に遠征を出した時点からカウントが始まります。
- **demo 倍率（`getDemoSpeed`）は掛けません**（負傷の回復と違う扱い。遠征の完了自体は加速で早まるので、進む量は自然に短くなる）。
- 猶予は**行動時間24時間相当**。値と段階の閾値は `data-time.js` の `masterMissingClock` が持ちます（調整前提）。
- 実装：本人の `missing` に確定分（`baseMs`）と進行中区間の開始（`anchorStart`）を持ち、遠征の完了時に実完了時刻までを確定します（負傷と同じく絶対時刻ベース＝閉じている間も正しい）。

### 状態とUI

- 行方不明者は**名簿に残ります**。`status: "行方不明"` になるため既存の判定でそのまま**編成不可**です。負傷は持ちません（手当てを受ける本人がいない）。
- ★ **数字の残り時間は出しません。段階だけ出します**（3段階。閾値 0〜40%／40〜80%／80%〜はデータ側）。**文言は 2026-09-11 に本置き**（EX-072）：

| 段階 | 事実の行 | 添える行（{名前}） |
|---|---|---|
| 1 | 消息を絶っている | なし |
| 2 | 消息を絶ってから、しばらく経つ | {名前}に焦りが見える |
| 3 | 消息を絶ってから、だいぶ経つ | {名前}の表情は暗い |

- ★ **「手掛かりが薄れつつある」「絶望的」は採りませんでした**（仮置き文言）。あれは現場を見た者の評価で、**現場にいない記録係には書けない**。書けるのは「事実」と「目の前にいる人の顔」だけ、という線です。
- **{名前}＝その者と最後に同じ遠征へ出ていた者**。行方不明になった当の報告書の参加者（`report.adventurerIds`）から導き、**新しい値は持ちません**。自分自身と、自分も行方不明・死亡の者は候補から外します。複数いるときは**参加者順（＝編成順）の先頭**を採ります（固定順。関係値ができたらそこで選び直す）。
- **該当者がいないとき**（単独遠征・参加者全員が行方不明・報告書が見つからない）は**受付嬢の名前**（`data-adventurers.js` の `masterReceptionist`＝アルメナ）を入れます。★ **仮置き**で、関係値ができたら差し替えます。

### 基本式（更新: 2026-07-25）

- stat：**育成6種のみ 0〜255**（内部小数・表示整数）。初期値は得意25〜30／平均15前後／苦手10（実値は `data-adventurers.js`）。成長は上限255（**式はスライス10の成長システム節を参照**）。**性格値5種は `tendencies`（1〜5・育たない）へ分離済み**（2026-07-31）。旧スケールのセーブは読込時にマスター初期値へ自動移行。
- ★ **255 という数字に根拠はありません。** 作者が「えいや」で決めた値だと確認済みです（2026-07-31）。コード・`docs/`・Notion のコアコンセプト18章のいずれにも選定理由はなく、18章は冒頭から **255 を既に存在する前提**として扱っています。**それでも変えません**（意味づけ＝初期10〜30／3ヶ月で150前後／255は長期目標、は 255 を前提に組み上がっており、動かす利得がない）。**「255には意味がある」と読まないでください。**
- 与ダメ＝ `√combat × 3.5 + weapon.power × 2`、分散 0.75〜1.25。**`power` は 0〜50 で持ち、式に入るのは `BATTLE_TUNING.powerScale`（1/10）を掛けた値**（2026-07-30。guard と同じ流儀に揃えた。実効値は据え置きで、バランスは変えていない）。
- 味方HP＝ `job基礎値 + survival × 0.6`（基礎値：盾役110／戦士95／斥候78／薬草師72／未知職85）。初期実値：ロウ125／ガッド104／ミナ89／エルネ79。
- 敵：野盗 **HP320 / threat38**、納屋 **HP240 / threat38**（`data-enemies.js` が正本）。2026-07-30 に**一撃が重い敵**（大熊 HP260/threat46）を1種追加したが、★**どの依頼にも割り当てていない**（既存の依頼の敵を差し替えると基準値が全部動くため。`scripts/measure-enemy.js` の中だけで別条件として測る）。
- 被ダメ配分：前衛60%・残り40%を他の人間で等分・エルシー0%。前衛は**HP率降順（交代制＝H1-a・2026-07-29）**で選び、同率のときのみ job順（戦士＞見習い盾役＞斥候＞薬草師）→ **`tendencies.courage`** の高い方
- **guard（2026-07-30）**：被ダメは「その人の取り分 − guard」の**減算**で、下限は0のみ。guard の役割は「連続攻撃に強い」ことなので、乗算にはしない。**武器の `guard` は 0〜50 で持ち、実際に引くのは `BATTLE_TUNING.guardScale`（1/10）を掛けた値**（実値は `data-adventurers.js` が正本）。0〜5 では1目盛が粗すぎ、1動かすと軽が5pt動く（`lightWoundRatio` 1目盛と同規模）ため刻みだけを細かくした。**実効引き量は据え置きで、バランスは変えていない**（同一シード3000本で変更前と結果が完全一致）。
- ★ **guard は成長しない。** 育成6種と違い、装備が決めるものなので育つ数値とは別に扱う（理由と却下案は DECISION_LOG）。武器の `power` も同じ扱い。
- maxRounds 8。大ヒット「！」＝与：損耗後期待値×1.08以上／被：被弾者maxHp×0.12以上（スケール非依存）。
- **クリティカル（2026-07-30／閾値は 2026-07-31 追加）**：与・被の双方で1発ごとに判定し、命中ダメージを倍にする。0ダメージの被弾では判定しない。発生率・倍率は `BATTLE_TUNING`（`critRate` / `critMultiplier`）が正本。**上限は設けない**（HP0 は死ではなく行方不明＝捜索チェーン行きなので、即死条件はもともと満たされている。上限を入れると意図的に殴られることが安全になり自爆成長を許可する）。
  - ★ **受ける側は、素ダメージが受け手の maxHp 比で小さすぎる一撃も判定しない**（`critMinHpRatio`）。かすり傷で「致命の一撃を受けた」と書かれ、重症で帰されるのを止めるため。**判定をしないだけで総ダメージは動かない**（下限を入れて底上げする案は却下。底上げすると軽が下がり `lightWoundRatio` の再調整が連鎖する）。
  - ★ **受け手の maxHp 比で持つ理由**：「致命の一撃と呼べる重さか」は**受け手基準の不変量**で、ロウ（125）とエルネ（79）で意味が変わってはいけない。敵の `threat` 比で持つ案は却下＝**致命かどうかを相手の都合で決めることになる**。
  - 与える側には閾値を入れていない（基準4人での最小表示が12ダメージで、不自然さが出ていないため）。

#### ★ 防げた瞬間と、使わなかった支給品（2026-07-31）

戦闘依頼（`enemyId` を持つ依頼のうち隊商護衛以外）の報告書には、次の2種を書きます。**畑の追い払いが戦闘のチュートリアルにあたるため、「うまく送れたときも理由が読める」ようにするためのものです。**

- **防げた瞬間**：`roundLog` に既にある事実（guard で0に抑えた被弾・前衛の交代）を拾って書きます。**新しい値は持ちません。**
  - ★ **全部は書かず、最も効いた1〜2個だけ**（「書くのは変化があったときだけ」を守る。長くすることと、起きたこと全部を書くことは別）。
  - **深手・戦闘不能が出た戦闘では書きません**（そちらが書くべき変化なので）。
  - 誰が前を塞いだから誰に届かなかったのか、**名前で結びます**（編成の効果を因果として書く）。
- **使わなかった支給品**：「使わなかった」ではなく**物の状態**として書きます（例：包帯は封を切られないまま戻ってきた）。
  - **持たせたのに使わなかったときだけ**書きます。持たせていないものは書きません＝**支給品を持たせた判断が正しかったかの手がかり**になります。
  - ★ **「使った」と「使わなかった」は、どちらも事実（イベント）に合わせます**（2026-09-12・EX-082）。抽選で書くと同じ報告書に両方が並びます。実際に **4依頼×3品**で起きていました——納屋の包帯 12%／手紙・廃屋の油紙は**晴れ以外 100%**／夕市の笛 20〜40%。
    - 原因は3つで、**独立していました**：①依頼固有ログが事実を見ずに「使った」と書く（納屋）②「使わなかった」側の条件が道具の効く条件と揃っていない（油紙の雨判定が「小雨」だけ。工程エンジンは**天候負荷が0より大きければ**使う）③**生活依頼フローが `supplyEventText` に天候を渡していなかった**（渡し忘れ）。
    - ★ **抑制するときは抽選を済ませてから落とします**（EX-071 の樽と同じ形）。乱数の消費が変わらないので、**結末・あらすじ・滞り件数は動きません**（11,400件で不一致0。行数が変わるのは嘘の行が消えた分だけ）。
  - 挑まずに引き返した回と、誰かが負傷して帰った回では書きません（前者は出番がなく、後者は「要らなかった」ではないため）。

#### ★ 変化のない被弾は1行に畳む（2026-08-04・EX-052）

隊商護衛の交戦ドラマログでは、**状態が変わらず・強打でも致命でもない被弾**を、そのラウンドの最初の1件の位置に**1行へ集約**します（合計ダメージを添える）。

- ★ **上の「防げた瞬間」と同型の適用です。** あちらは 0ダメージに抑えた被弾を1行に畳みました。**変化のない事象を1行にまとめる**という同じ形を、別の場所に当てただけで、**新しい文型ではありません。**
- 実測では**被弾の 71.1% が状態も変えない削り**で、**すべての報告書で同じ人が3〜5回それを受けて**いました。個別に書くと同じ行が1つの報告書に3〜5回並びます。
- ★ **合計ダメージを残すのは、消耗の蓄積が読めないと撤退が唐突になるからです。** 撤退判断は4段階・多数決で**消耗の蓄積を前提**に組んであるので、全部落とす案（変化のない被弾は書かない）は採りませんでした。
- ★ **攻撃行（与ダメ行）は畳みません。** 毎回ダメージが入っている＝変化のある事象なので、この規則の対象外です。
- 攻撃行は代わりに**職ごとの文の数を揃えて**あります（並打ち：戦士2・見習い盾役2・薬草師3・斥候3）。2026-08-04 まで**斥候だけ1文**で、これは設計ではなく漏れでした。★ **揃えるのが目的なので、それ以上は増やしません。**

> 現状これが書けるのは**包帯だけ**です。笛やランタンは「使った」を判定できる場所がなく（ログ文の抽選で決まる）、煙幕は畑・納屋では持たせられません。

#### ★ 「取るに足らない被弾」は1つの概念。ただし適用する単位が違う（2026-07-31）

**取るに足らない被弾はクリティカルにも負傷にもしない。** 同じ概念に2つの値を持たないため、両方が `critMinHpRatio` を共有します。**ただし当てる単位が違います。**

| | 判定の単位 | 理由 |
|---|---|---|
| クリティカル（＝深手） | **1発あたり** | 「その一撃が致命か」を見るので単発で正しい |
| 負傷（軽症・重症） | **累積** | 「取るに足らなかったか」は**結果に対して**判定する |

- 負傷は、**合計被ダメージが maxHp の 5% 未満なら無傷**。それ以上なら従来どおり帰還時のHP率で決めます（`injuryHpRatio`）。
- HP そのものからは常に引きます（消耗が戦闘の継続と撤退判断に効くのは正しいため）。
- 狙いは**「何も起きなかった日」を作ること**。ドラマは対比で効くので、無傷で帰る遠征がないと、傷を負った遠征が際立ちません。
- ★ **1発ごとに5%未満を捨てる実装を一度作って、同日中に直しました**（履歴として残します）。それだと 4% の被弾を8回受けた者＝32%を失った者まで無傷になり、報告書が「手負い」と書くのに名簿が「無傷」と言う状態になりました。**その食い違いは、直すべき表示ではなく、実装が間違っているという表示でした。**

> ⚠️ **5% という値に意味はありません。**
> `critMinHpRatio` の 0.05 は、**現在のダメージ分布の谷の位置**（4人編成では前衛シェア0.6と後衛の頭割り0.4÷3の構造で、threat38 なら後衛1〜4／前衛12〜26と分かれ、5〜11が空になる）から**経験的に決めた値**であって、世界の定数ではありません。
> 負傷の下限が同じ 5% なのは、**そこから借りたから**です。一致は発見ではありません。
> ★ `GROWTH_STAT_MAX = 255` と同じ形にしないこと（「255には理由がある」と後から信じられるのを避けるため、根拠がないことを明記してあります）。
> **敵の種類が増えたときは谷の位置を測り直してください。谷が動いていたら 0.05 も動きます。**

### 状態語と損耗DPS（更新: 2026-07-25）

- 状態語4段階：健在／手負い（HP70%以下）／**深手（＝クリティカルを受けた。2026-07-30。HP率による判定は廃止）**／戦闘不能（0）。遷移した瞬間のみログに出す。深手は手当て（包帯）で解除される。
- ★ 深手を「累積」から「事件」へ変えた理由：前衛の交代制（H1-a）が累積を払うため深手が 0% になり、臨時撤退・煙幕・エルシー・支給品の価値がすべて止まった。しきい値の調整では両立点が存在しないことが掃引で証明済み。
- 損耗DPS低下：与ダメが状態語連動で 健在100%／手負い80%／深手50%。

### 回復（更新: 2026-07-25）

### 撤退判断＝4段階（更新: 2026-07-30・作り直し）

★ **撤退が成立するのは段階4だけ。** 段階1（接敵）だけが例外で、そこでは戦わずに引き返せる。

| 段階 | いつ | 何を見るか | 成立 |
|---|---|---|---|
| **1. 接敵** | 戦闘開始前 | **予想ラウンド数**（下記 forecast）と医療品の残り。★ここで引ける＝挑まずに帰る | **半数以上** |
| **2. 想定超過の被害** | 深手/戦闘不能が出たラウンド末（上限2回/戦） | 動揺（旧・臨時判断のまま） | 半数以上 |
| **3. 帰ろうと考える者が出始める** | 段階2が一度起きた後 | 以降は**毎ラウンド**段階4を回す | − |
| **4. 相手の様子を見て決める** | 段階2/3の直後（毎ラウンド） | forecast ＋ 相手の残りHP ＋ 医療品の残り | **半数以上** |

- **forecast＝「倒すまでのラウンド数 ÷ こちらが持たないラウンド数」**。倒すまで＝敵HP ÷ 損耗後の与ダメ合計。**1.0 で互角**。
  - **持たない＝次の2つの短い方**（2026-07-31）：パーティ総HP ÷（threat − 生存者の guard 合計）と、**前衛の現HP ÷（threat × 前衛シェア − 前衛の guard）**。
  - ★ **総HPだけで見ると前衛60%集中を無視するので、判断が実態とずれる**（ミナ+ガッドは比1.21＝やや不利と読まれていたが、実際の勝率は 1.6〜16%だった）。**崩れるのは総量ではなく列**。「判断は常に正しい」を守るための精度修正。
  - ★ **これで初めて敵の threat と最大HPの絶対値が判断に入った。** 旧式は敵HPの**割合**しか見ておらず、割合は接敵時に必ず 1.0 なので**野盗と大熊で接敵スコアが完全に同じ**だった。
  - スコア＝ `(forecast − 1) × forecastScoreScale + forecastScoreOffset` ＋修正。閾値は従来どおり job基礎（斥候50／薬草師55／盾役65／戦士80）±personality（慎重−10／豪胆+10／我慢強い+10）。**値は `BATTLE_TUNING` が正本**。
  - **損耗は forecast の中（現在HP）に入っているので、旧式のように別項では足さない**（二重計上を避ける）。
- **医療系支給品は「残り個数」で効く**：残っている間は「手当てできるからまだやれる」（**−10**。2026-09-13 に −20 から下げた＝EX-091）。**使い切った瞬間に効かなくなる**＝あるから粘り、なければ引く。使い切ったことは報告書に出す。段階1・段階4の両方で効く（包帯は**勝つ手段**の側だから）。
- ★★ **一般則（2026-07-31）：判断に入るのは「勝てるか」に関わるものだけ。「逃げやすいか」は撤退の成否にだけ効く。** 人が撤退を決めるのは「勝つ手段がもうない」と思ったときで、「逃げ道があるから逃げよう」ではない。
  - **煙幕もエルシーも「逃げる手段」なので、段階1・段階4のどちらでも判断に入れない。** 効くのは**撤退の成否**（煙幕は成功率を上げる／エルシーがいれば必ず成功）と**結末**（partial_loss / partial_detour / partial_elsie）だけ。判断に足していたときは、勝てる編成が煙幕を持っただけで離脱していた（3人＋エルシーの交戦後撤退 1.3% → 35.1%）。
  - **包帯は「勝つ手段がまだある」側**なので判断に入れてよい（継続寄り）。
    - ★ **重みは −10**（2026-09-13・EX-091。それまでは −20）。**包帯を判断から外したのではなく、大きさだけを下げています。**

## 非戦闘依頼の共通経路（工程エンジン）（更新: 2026-07-31・実装済み）

`enemyId` を持たない依頼が通る経路。実装は `app.js` の `FIELDWORK_TUNING` / `simulateFieldwork`。**この節が現行実装値の正本**です。

内訳は 戦闘経路3件 / 工程エンジン13件（うち2件は結末を動かさない）/ 据え置き1件。

移行前は、非戦闘依頼の結末が候補配列からの `pickOne` だけで決まっていて、**編成を変えても支給品を増やしても分布がほぼ動きませんでした**（実測済み）。依頼の性質ではなく実装都合で安全度が分かれている状態を解消するための経路です。

### 規則

- **非戦闘に撤退判断は入れない。** 撤退判断は「こいつに勝つ手段がもうない」を判定する仕組みで、**非戦闘には勝敗がない**ので対応する概念がない。「引き返す」は成果の程度なので**結末の格下げ**（完遂→部分→未達）で表す。
  - ★ 副次的に、戦闘側の撤退を直しても非戦闘は動かない（切り分けが保てる）。共有した瞬間にこれが壊れる。
- **非戦闘の「敵」は天候と疲労の2つだけ。** 道中の事故・時間帯・依頼固有の脅威は後回し（依頼ごとの書き分けが発生するため）。
- **天候と疲労は別々に持つ。** 畳むと「何のせいで失敗したか」が報告書に書けない。天候＝遠征中ずっと乗る固定値、疲労＝**遠征中だけ**のカウンタ（ユニットの永続状態としては持たない）。
- **判定に使う育成値は `GROWTH_STAT_BY_CATEGORY` から導く。** 対応表を新設しない＝**「その依頼で伸びる stat ＝ その依頼で使う stat」**。これで exploration / investigation / negotiation が初めて判定入力になった。
 - ★ **工程ごとに別の育成値を宣言できます**（`quest.fieldworkSteps`・2026-08-06・EX-054）。宣言した工程だけその育成値で判定し、**宣言のない工程はジャンル表のまま**（ジャンル表は廃止しない）。★ **宣言は工程数を決めません**（2026-08-13・EX-057 で切り離した。数は `fieldworkPhases`＝下記が持ち、工程数より宣言が少ない依頼は余った工程がジャンル表を見ます）。
 - ★ **成長側は「その回に実際に使った育成値の和集合」（`hiddenTags.fieldwork.stats`）だけを読みます。** 依頼データを直接読まないのは、**対応表を1つに保って登録漏れを防ぐため**。
  - ★ **2026-09-13・EX-093 に `hiddenTags.growthStats` を足しました**（工程エンジンを通らない依頼も
    同じ形で主成長セットを宣言できます）。**`growthStats` があればそちらが勝ち**、無ければ

## 報告書ログ順序フェーズ案

現時点では設計メモであり、まだ `phase` 実装はしない。

共通フェーズ案：

1. `departure`: 依頼内容・出発
2. `arrival`: 現地到着
3. `situation`: 状況確認・最初の違和感
4. `action`: 作業 / 移動 / 探索 / 交戦
5. `choice`: 冒険者の判断
6. `support`: 支給品・個性の反映
7. `result`: 結果
8. `return`: 帰還
9. `afterglow`: 余韻
10. `highlight`: 今回のハイライト

方針：

- 毎回すべてのフェーズを使わない
- 生活・輸送・保全では不穏さを抑える
- 捜索・戦闘では結果を早く漏らさない
- 調査・記録では未解決や判読不能を自然に残す
- エルシーログは主作業の邪魔をしない位置に置く
- ハイライトは本文と矛盾させない

## 観察記録票 / 報告メモ / 生態目録（更新: 2026-09-17・EX-123）

### 観察記録票（更新: 2026-09-16・EX-109）

- 観察対象がある依頼で意味を持つ
- 観察記録票を持っている冒険者だけが観察メモを書く
- 観察メモは報告メモへ蓄積される
- ★ **観察メモは「{名前}は…」の形で書きます**（2026-09-16・EX-109 の裁定4）。報告メモには複数人の記録が並ぶので、**文体が揃っていないとそこだけ浮きます**。⚠️ **例外は森喰い兎の14文で、これだけ名前を含まない地の文です**（体験版①より前からある古い分岐。今回は揃えていません）。
- ★ **観察メモの文は3段階で選ばれます**（2026-09-15・EX-105）：
  1. **対象ごとの専用分岐**（森喰い兎／「なにか」／残る灯り／灰かぶりのような『なにか』）
  2. **種別ごとの既定**——依頼データの `observationKind`（生態目録の分類語。獣／植物 など）で引く
  3. 種別が書かれていないときの**受け皿**
  - ★ **観察が主眼の依頼は専用分岐にします**（2026-09-15・EX-108）。種別の既定は**他の依頼にも効く**ので
    **対象の固有名を出せません**。名が文に出ないと、**命名の対象として立たない**ためです。
  - ★ **段は「好奇心 → 記憶 → 既定」の順に見ます**（2026-09-16・EX-109 の裁定2＝案a）。⚠️ **元は記憶が先で、記憶と好奇心の両方が高い冒険者（ミナ＝記憶5・好奇心4）が好奇心の段に永久に入りませんでした。**
    現行5人で好奇心4以上はミナだけなので、**旧順では好奇心の段に到達する者が1人もいませんでした**。★ **順序を入れ替えても乱数の消費は変わりません**（どちらの段も `pickOne` を1回だけ引く）。実測でも 9,600組・10項目のうち**動いたのは観察記録の文だけ**（480件。すべてミナが書いた回）。
    ※ 冒険者側の値を動かす案は**却下済み**（値は他の全判定に効くので、文のために動かすのは順序が逆）。
    ※ **森喰い兎だけは好奇心の段を持たない**ので対象外（記憶と職・気質・前職で分岐する形）。
    ★ **これで到達不能だった11文のうち8文が出るようになりました**（灰かぶり2／畑の「なにか」2／残る灯り2／種別「獣」2）。残る3文（種別「植物」の好奇心2・受け皿の好奇心1）は**順序の問題ではありません**。⚠️ **「植物」と「受け皿」の表は今どの依頼からも引かれていません**（唯一の植物依頼＝灰かぶりが専用分岐を持ち、種別の付け忘れも0件のため）。**表ごと未使用**なので、記憶・既定の段を含む計9文が出ません。★ **これは穴ではなく備え**——専用分岐を持たない植物依頼を足せば、その時点で出ます。★ **未使用のまま残します**（2026-09-16・EX-110 の裁定2）。⚠️ **「到達不能」とは理由が違います**——到達不能だった11文は**段の順序**で入れなかったもので、順序を直せば出ました。こちらは**表ごと引かれていない**（＝その種別の依頼がまだ無い）だけなので、**依頼を足せばそのまま出ます。消しません**。
  - ⚠️ ★ **旧実装は 2 と 3 が無く、専用分岐の無い対象を「短い観察だったため、詳細な記録はできなかった」に落としていました。**
    観察記録票を持って行った者が書いた紙なので、**票を持たせた回ほど嘘になる**形でした（納屋が実際にこれに落ちていました）。
- ★ **観察記録は沈黙して落ちる穴が2つあります。** どちらも画面にもログにも何も出ません。
  1. 対象を持つのに**専用分岐も `observationKind` も無い**（受け皿の文になり、対象に合わない記録が出る）
  2. 報告書の組み立てが **`observationNotes: null` を直書き**している（**1行も出ない**）
- ★ **`null` と「空の配列」は別の意味です**（2026-09-17・EX-117）。
  **`null` ＝対象がいなかった**（定型報告書／夜道の昼ルート／挑まずに引き返した回）、
  **`{ notes: [] }` ＝出会ったが記録票を持たせていなかった**。⚠️ **以前は両方 `null` だったので、
  「出会ったのに生態目録の枠が立たない」と「いないのに立つ」を区別できませんでした。**
  報告書の文面は変わりません（`notes` が空なら観察記録票の欄は1行も出ません）。

  - **A 推測**＝自由記述。プレイヤーが書きます
  - **P 次に確かめたいこと**＝自由記述。プレイヤーが書きます

  - ★ **同じ軸に複数件を書けます**（行を足す）。観察は回を重ねるもので、**別の遠征で見た「動き」を

  - ★ **どこにも属さない観察が出たら、備考に逃がさず軸を足します**（2026-09-17 の裁定）。
    受け皿を残すと、軸に振る手間を避けて全部そこへ流れ、SOAP に分けた意味が消えるためです。
    ⚠️ **「その他」という13番目の軸も置きません**（名前が違うだけで備考と同じものになります）。
- ★ **12軸の目的は2つあり、向きが逆になります**（2026-09-17 の裁定）。
  - **通常のいきもの**：軸は**埋めるほど良い**。分かるほど扱いやすくなります。
  - **反ミーム的なもの**：軸は**埋めるほど危険**。記録が増えるほど、こちらが掴まれます。
  - ★ **同じ12軸が逆向きに使われる**のが要で、**軸を2系統に分けません**。
    分けると、プレイヤーは**雛形を見ただけで相手の正体を知ってしまいます**。
  - ⚠️ **反ミームだけ専用の雛形にする可能性は残します**（同じ軸で足りないと分かったときに限ります）。
- **外側（標本ラベル）は名前／分類／遭遇地域**。名前と遭遇地域は自動欄なので**編集できません**。
- ★ **分類欄は依頼データの `observationKind` から自動で入りません**（新規は必ず「未分類」から始まります）。**2026-09-17 の裁定でこれが正しい形になりました**——**分類はプレイヤーの仕事**なので、データ側に語彙があっても繋ぎません。
- ★ **命名は12軸中7軸で解禁します**（2026-09-17・EX-118 の裁定1）。
  O（確かめられたこと）の**軸の種類**が7つ以上になると、名前の欄と確定印が出ます。
  - ★ 数えるのは**軸の種類**であって件数ではありません。同じ軸に3件書いても1軸です。
  - ★ 「移行前の記述」は数えません（旧セーブの逃がし先で、軸に振っていないため）。
  - ⚠️ **7は暫定です。** 反ミームに必要な項目数が確定したら見直します。
  - 軸を書き足したら、いったん保存して開き直すと名前の欄が出ます。
- ★ **命名は確定印を押して確定し、以後は編集できません**（裁定2）。読了ハンコとは**別の判子**です。
  - 確定前は何度でも書き直せます（下書きは `nameDraft` に残り、確定で `name` へ移ります）。
  - ★ **確定印の前に確認を1回出します**（取り返しがつかない操作のため）。
  - ★ 確定するのは**名前だけ**です。分類・O・A・P は確定後も書き足せます。
  - ⚠️ 解禁条件と確定済みの判定は**画面と保存の両方で見ます**。画面の守りだけにしていません。
- ★ **答え合わせ（報告書に隠した語との照合）は実装していません**（裁定3）。命名は自由入力のまま通します。
  2026-08-06 の「めちゃくちゃなことを書いて OK にはしない」は**保留**です
  （理由は DECISION_LOG 2026-09-17 を参照。12軸中7軸を埋めるには報告書を読む必要があるので、部分的には担保されています）。
- ★ **確定した名前は題名まで及ぼします**（2026-09-17 の裁定）。生態目録のページの中だけには留めません。
  - ★ **参照化は段階に分けます**（第一段＝題名・掲示板・生態目録）。
    ⚠️ **一度に全部を置き換えません**。題名・掲示板・報告書・敵の短縮名は生成の経路が別々で、
    同時に替えると**どこで壊れたか切り分けられない**ためです。
  - ★ **第一段は実装済みです**（2026-09-17・EX-119／EX-120）。確定した名前が及ぶのは
    **「今の状態」を出す画面だけ**——**掲示板（カードの題名／観察対象欄／待機中の帯）・遠征中・編成画面**と**生態目録**です。
    - ★ **依頼データ（`title` ／ `observationTarget`）は書き換えません。** 描画のたびに引く形なので、
      **報告書の本文・報告メモ・冒険者の履歴（保存済みの文字列）は当時の呼び方のまま**残ります。
    - ⚠️ ★ **報告書には及ばせません**（2026-09-17・EX-120 の裁定）。見出しも本文も**当時の呼び方で閉じます**。
      理由：命名より前の報告書で見出しだけ確定名にすると、**同じ紙の上で呼び名が割れる**からです。
      ★ **第二段でも揃いません**——第二段が及ぶのは**これから生成される報告書**で、
      **過去の報告書は当時のまま**という裁定だからです。割れたままにするくらいなら、**一枚の記録として閉じます**。
    - ⚠️ **仮称を題名に含む依頼は3件**（畑の「なにか」／夜道の残る灯り／納屋の嚙みつく「なにか」）。
      ★ **納屋だけは題名の「噛」と観察対象の「嚙」で字が違う**ので、**表示だけの別名**で吸収しています
      （データを揃えると生成される本文まで変わるため。`QUEST_TITLE_ALIASES`）。
    - ★ **第二段も実装済みです**（2026-09-17・EX-121）。**命名が確定したあとに生成される報告書**は、
      **本文・観察文・交戦ログ・観察記録票**まで確定名で書かれます。
      - ★ **一枚の中では必ず呼び名が揃います**——命名前の報告書は全部仮称、命名後の報告書は全部確定名。
      - ★ **生成の出口で置き換えて、そのまま保存します。** あとで名前が変わっても**過去の報告書は動きません**。
      - ⚠️ 置き換えるのは**本文が実際に使っている呼び名**（`QUEST_NAME_ALIASES`）です。
        仮称そのものは本文にほとんど出ません（畑と納屋は 「なにか」、夜道は 「灯り」。仮称「残る灯り」は本文に0回）。
      - 交戦記録の短縮名は `enemyDisplayShortName` で引きます。★ **敵5体すべてが `shortName` を持ちます**
        （2026-09-17・EX-124 の裁定＝案A で納屋に追加。⚠️ **それまでは納屋だけが持たず、交戦記録が「相手」に落ちていました**
        ——本文は「なにか」と呼ぶのに交戦記録だけ呼び名が違う＝**同じ紙の上で割れている**状態で、実測で 40/40 本・計208行）。
        ★ **納屋の短縮名は 「なにか」**（畑と同じ）。漢字を使わない形にしてあるのは、題名の「噛」と観察対象の「嚙」で
        字が違い、どちらかを借りると表記ゆれを抱え込むためです。※ **畑と同じ短縮名になるのは是認**
        （別個体だが「同じものかもしれない」という含みが残る）。
        ※ **持たない敵を検出する検査は置いていません**（EX-124 の案D。敵は5体でコストに見合わないため。★ **敵が増えたら再検討**）。
      - ★ **あらすじの「正体はまだ不明」は命名後も残します。文面も変えません**（2026-09-17・EX-122 の裁定）。
        ★ **名づけは同定ではありません**——名前を与えても、それが何であるかは分かっていない。
        灰かぶりの依頼で書いた**「どこまで在るかは分かった。何であるかは分からない」**と同じことを、あらすじが言っています。
        ★ **答え合わせを実装していない**（暫定で見送り）こととも整合します——**プレイヤーが付けた名前が正しいかは、誰も保証していません**。
- **旧セーブの移行**（`schemaVersion` は据え置き）：名前キー → id キーへ移し替えます。
  旧「次に確認したいこと」は P へ、**外見・特徴／備考／旧5欄は「移行前の記述」欄に丸ごと**置きます。
  ★ **軸へは自動で振りません**——どの軸のことかを決めるのは分類と同じくプレイヤーの仕事だからです。
  仮称がどの依頼の `observationTarget` にも一致しないエントリ（旧実装で名前を書き換えてできた残骸）も
  **落とさずに移します**。独立したページとして残り、S が空になるだけです。

## データ保存（更新: 2026-07-26）

- `localStorage` に保存（単一キー）
- **`state.schemaVersion`（現在3）でセーブ世代を管理**：番号不一致なら初期化（モック段階の割り切り）。★**発動条件を固定：配布ビルドを作る前に必ず個別移行関数方式へ切り替える**（2026-07-29確定。version フィールドを持つことは既に満たしており、移行関数を書くことは可逆なので今は書かない）。schemaVersion不在の旧世代は内容推定の移行（旧statスケール置換等）で受け入れる
  - ★ **「配布ビルド」に身内向けが入るかは未確定**（2026-08-03）。体験版は**身内向けのアルファ未満**で公開配布ではないと確定したため、この発動条件を満たすかどうかが読みで割れます。**配る前に必ず決めること**（発動条件は解釈で回避できると意味が消えるため、ここに未確定であることを書いておきます）。
- `quests` / `items` はマスターデータを正として使う
- `adventurers` はマスターデータを基本にし、`favorite / memo / history / status / stats / nickname` を保存対象として反映する（nicknameは体験版①で保存漏れを修正）
- 閉じている間に遠征が完了していた場合、再訪時はホーム最上部の「今回の帰還」カードから確認する（起動中の帰還は従来どおり全画面リザルト）
- ★ **依頼が見つからない遠征は中断する**（2026-09-14・EX-097）。`state.expedition.questId` が
  `masterQuests` に無いとき、`checkExpeditionCompletion` は**所要時間を待たずに遠征を畳みます**。
  - 畳み方：**冒険者を待機中に戻す**（★ 行方不明の者はそのまま）／**暦は進めない**／**報告書は作らない**／
    行方不明の時計はその遠征ぶんだけ積んで止める／`console.warn` を1行出す。
  - ★ **報告書を作らない理由**：死んだ `questId` の報告書を残すと、解放条件（`getClearedQuestIds`）と
    報告メモにその id が混ざります。**画面が落ちなくなる代わりに記録が汚れる**のは割に合いません。
  - ★ **冒険者は失わせません**（「プレイヤーを責めない」）。データの都合で人が消えるのは主題に反します。
  - 起きるのは**依頼を入れ替えたとき**（v2 へ作り直す／実験的な依頼を足して消す）で、
    **通常の遊び方では作れません**。それでも入れたのは、放置すると `render()` が毎秒落ちて
    **画面ごと出なくなる**＝損害が大きすぎるためです。
- `selectedAdventurerItems` は旧形式（`advId: "itemId"`）から新形式（`advId: ["id1", "id2"]`）へ自動変換する
- `reports` / `reportMemos` / `ecologyRecord` を保存する。★ **`ecologyRecord` のキーは id**（2026-09-17・EX-117）。
  旧セーブ（名前キー）は読み込み時に移し替えます（`schemaVersion` は据え置き。前例3つ＝アイテム欄の正規化／生態目録の旧フィールド統合／読了ハンコ）
  - ★ **旧キー `beastLog` からも読みます**（2026-09-17・EX-125 で内部名を改めたため）。

    ⚠️ id は生態目録の中でしか使われず、報告書は仮称で引くので、振り替えてもつながりは切れません）。
    ★ ここでも `schemaVersion` は上げません（**上げると報告書も名前も全部消える**ため）。
